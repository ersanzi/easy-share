# 2026-10-21 · 会议纪要 skill 提速与区间转写

## 用户问题

1. 用 Agent 跑 `skills/minutes-from-transcript` 生成纪要**还是很慢**，但不想为了快牺牲输出效果（钉钉版式的报告密度要保住）；
2. 逐秒区间格式`[00:00 - 00:00] 嗯,` / `[00:00 - 00:01] 行嘞行,` 这类 ASR 分段导出，喂进去解析不对。

宿主不固定（Claude Code / Codex / WorkBuddy 等都可能用），所以提速不能依赖某一家 Agent 的特有能力。

## 目标

- 正确解析 `[起 - 止] 正文` 的逐秒区间格式，包括正文含冒号、纯语气词行、单行 SRT 写法；
- 在不删减 `topics` / `visual`（报告密度来源）的前提下，减少模型必须生成的重复字段与请求次数；
- 减少 Agent 侧的上下文与往返开销：不读请求大 JSON、不把模型原始输出重新序列化成 JSON 字符串；
- 长会可选两阶段拆议题，避免「按时间硬切」把同一件事写成两半；
- `run` 与知识服务 `build()` 路径行为不变。

## 非目标

- 不改知识服务侧的录音采集、实时字幕、ASR 与任务队列；
- 不改产物结构、Word 版式、色卡与长报告模板；
- 本轮不做真实模型的墙钟基准（没有稳定端点），只验证「请求数 / 输出字段 / 材料长度」这些结构性变化与端到端产物。

## 设计决策

1. **区间时间戳按行优先识别，说话人判定收紧。**
   `engine/minutecraft/transcript.py` · `_parse_plain_line` 的优先级是 `_RANGE_TS` → `_BARE_RANGE` → `_TS_ONLY` → `_SPEAKER_ONLY` → 普通行；起止分隔符支持 `- – — ~ ～ --> 至 到`，时间支持 `mm:ss` / `hh:mm:ss` / 带毫秒。
   此前 `[00:01 - 00:02] 那我们开始吧，今天主要过三件事：…` 会把冒号前的半句当成说话人、后半句当正文。现在 `_looks_like_speaker` 只认角色标签、2-4 字中文姓名、拉丁名，长句/停用词一律不算说话人。

2. **单行 SRT 正文保留，路由按「时间轴是否独占一行」判定。**
   `_from_srt` 保留箭头后的正文；`load_transcript` 只有出现 `_SRT_BARE_LINE`（时间轴独占一行）才走 SRT，否则按普通文本解析。混排样例不会再被 SRT 解析器吞掉正文，也不会因为「解析出的 turn 多」而误选。

3. **材料压缩：默认合并同说话人短句、丢掉纯语气词。**
   `engine/minutecraft/models.py` · `render`（`compact` 默认开）与 `engine/minutecraft/textutil.py` · `is_filler` / `join_text`：合并同一说话人、相邻且间隔 ≤45 秒的短句（每段 ≤220 字，只在段首留时间戳），丢弃「嗯 / 行嘞行 / 好的好的」这类碎句。**原始 turns 一律不动**，转写附页与导出 JSON 仍是逐句。
   实测用户给的逐秒样例：15 行 ASR → 喂模型 2 行、336 字。

4. **不再让模型重复写可派生字段。**
   开启 topics 时，summary 不再要求 `chapters` 与 `mindmap`；`finish` 用 `engine/minutecraft/summarizer.py` · `chapters_from_topics` / `mindmap_from_topics` 从议题派生（议题的 title/start/end/gist 与章节同构，导图直接由议题 → 分组 → 要点拼出）。实测这两项占 summary 回答约 1/3 的 output token，而报告密度由 topics/visual 决定，不受影响。
   宿主不答 topics 时明确警告「chapters 与 mindmap 无法派生」，不静默降级。

5. **关键词并入 summary。**
   `engine/minutecraft/summarizer.py` · `_template_prompt` / `build_request` 的 `with_keywords`：Agent 两步走从 3 次请求降为 2 次（summary 回答里带 keywords），`finish` 仍接受单独补答 `answers.keywords`。`run` / 知识服务路径默认不开，原行为不变。

6. **Agent 侧不读大 JSON、不重新序列化。**
   `engine/minutecraft/cli.py` · `_write_prompt_files` 把每个请求的 system/user 写成 `request.prompts/<name>.<system|user>.txt`；`_resolve_answer_files` 支持 `answers.json` 用 `"@文件名"` 引用模型原始输出（相对 answers.json 所在目录解析）。SKILL.md 写明两条硬规则：不读 `request.json`、不把模型输出重新序列化成 JSON 字符串。

7. **两阶段议题（可选，`prepare --split-topics` + `expand`）。**
   长会把 topics 拆成「大纲（title/start/end/gist）」+「逐议题正文（focus/sections/insights）」：`engine/minutecraft/engine.py` · `expand` 用大纲时间窗经 `_slice_transcript` 切材料（±30 秒 margin），正文请求只带该议题片段，可并发；`_collect_split_topics` 合并时 title/start/end 以大纲为准。默认不开，短会不必多一次往返。

## 兼容与迁移

- 产物结构不变；`prepare` 返回新增 `derive_from_topics` / `topics_mode` / `prompt_files`，旧调用方忽略即可。
- `finish` 新增 `topic_outline` 允许键与 `topics_mode=split` 分支；`topics#N` 是新增键。
- `Transcript.render` 默认压缩；要旧行为传 `compact=False`（CLI `--full-text` 已接）。
- `run` / `build()` / 知识服务不受影响：keywords 仍单独调用（`with_keywords` 默认 False），summary 仍要求 chapters/mindmap。
- skill 副本已同步；无服务端改动、无 DDL、无安装包。

## 发布与回滚

- 本轮只改 `engine/` 与 `skills/minutes-from-transcript/`，不涉及控制面、知识服务、桌面端与安装包。
- 回滚：还原上述目录即可；请求包新增字段是加法的，旧请求包仍可被 `finish` 接受。

## 完成记录

- 已完成：区间格式解析、材料压缩、关键词并入 summary、chapters/mindmap 派生、提示词落盘与 `@文件` 回答、可选两阶段议题，以及 SKILL.md / README / examples 同步。
- 已知限制：
  - 提速是结构性的（少一次请求、少数两个重复字段、材料更短），实际墙钟收益随宿主与模型而异，本轮没有真实基准；
  - 材料压缩会把同一说话人的长段落合并到 220 字/45 秒，模型能看到的时间戳粒度随之变粗（分钟级），议题边界仍以行首时间为参照；
  - 两阶段模式的正文质量依赖大纲时间窗准确，时间抄偏会切偏材料；
  - `@文件` 路径相对 answers.json 所在目录解析，跨目录时要用相对/绝对路径写清楚。
- 下一步：用真实宿主跑一场 30 分钟以上的会议，对比「默认两步走 / `--no-topics` / `--split-topics`」的墙钟与报告密度；视结果决定是否按时长自动启用两阶段。
