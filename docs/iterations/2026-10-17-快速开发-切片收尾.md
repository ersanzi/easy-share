### 切片 5 — CfApi 占位符**接入生产**（本轮最大一步）

前几轮把 `internal/cfapi` + `internal/cfmount` 的机制真机验证完了，但**没有任何生产代码调用它们**——
摘要里那句「万级文件 0 字节占盘、点开才拉」此前只是包里的事实，用户摸不到。

| 交付 | 说明 |
| --- | --- |
| `cfmount_app_windows.go`（新增） | 把 CfApi 同步根挂到 `数据根/cloud-drive/personal`，与 WebDAV 盘**并列共存**（同一份内容两种呈现） |
| 登录态联动 | `refreshSpaceMounts` 挂上个人盘时同步挂 CfApi；重复触发有防重入（重复注册同步根会 `ERROR_ALREADY_EXISTS`） |

### 切片 3 — 冲突策略剩余两条规则

四条规则全部落地：

| 情形 | 规则 | 落在哪 |
| --- | --- | --- |
| 本地改 + 远端改 | 冲突副本，两份都留 | CAS + `conflictObjectKey`（已有） |
| 移动目标已存在 | 冲突副本，不覆盖 | `spacedav.Rename`（已有） |
| **远端新建 vs 本地已有、内容相同** | **认作同一文件（哈希去重）** | `sameContentOnRemote`（**本轮**） |
| **内容不同** | 保双方，加标记改名 | `conflictObjectKey`（已有，本轮补了哈希短路后的分支归属） |

**哈希去重解决的是一类具体恼人现象**：把**同一份内容**重新上传到同一路径、而中间别人动过它，
CAS 会拒绝、随后落一个「冲突副本」——于是云盘里出现两份**逐字节相同**的文件，用户还要自己判断删哪个。
现在按内容 MD5 判等，直接算成功。

- 判据用 `md5_reliable='client'` 的整文件读算（切片 6 落地）；
- **存疑一律按冲突处理**：远端无哈希、本地读失败 → 建副本。代价不对称——
  误判「相同」会吞掉用户这次写入，误判「不同」只多一份副本；
- 三处落地：`app.go` 单文件、`app.go` 文件夹、`spacedav` 资源管理器 PUT；
- 顺带把 `contentMd5` 加进 `FileVo`（列表透出），客户端才有得比。

### 切片 7 — 错误三件套

`internal/driveerr`（新增）：把任意失败翻译成 **业务码 + 人读文本 + 系统码**（对标钉盘 `TEC_*`、WPS `errorCode/errorMsg/winErrorCode`）。

| 层 | 交付 |
| --- | --- |
| 服务端视图 | 无（业务码由客户端按语义推测 + 服务端可读文案） |
| `internal/task` | `Task` 加 `ErrorCode` / `SystemCode` 两列 |
| `app.go` | `failTask()` 统一写三件套，替换 6 处裸 `"status":"failed"` |
| 业务码表 | `CLOUD_AUTH_REQUIRED` / `CLOUD_PERMISSION_DENIED` / `CLOUD_QUOTA_EXCEEDED` / `CLOUD_VERSION_CONFLICT` / `CLOUD_NOT_FOUND` / `CLOUD_NETWORK` / `CLOUD_STORAGE_ERROR` / `LOCAL_IO` / `UNSUPPORTED` / `UNKNOWN` |
| 前端 | `formatErrorDetail`：展示仍是人读文本，悬停给出业务码与系统码 |

**设计取向**：业务码是**稳定字符串，一旦发布不改名**（改名等于让历史工单/埋点失去可比性）；
识别顺序从具体到一般（业务语义 → 传输层 → 本地 IO），因为「配额不足」在网络层看只是个 HTTP 200。

### 切片 4 第 3 项 — 空目录持久化

原先 `pendingDirs` 只在进程内存：资源管理器里新建的空文件夹**重启即消失**（用户症状：「我建的文件夹自己没了」）。

- 新增 `internal/spacedav/dir_store.go`：`数据根/dirs.json`，按 space 分桶，临时文件 + rename 原子写；
- `Mkdir` 落盘、文件落地时 `clearPendingDir` 连同**祖先链**一起摘（`a/b/c.txt` → `a`、`a/b` 都不再为空）；
- `RemoveAll` 按前缀连带清理，删掉的目录不会在重启后复活；
- **诚实边界**：这是**客户端侧**持久化，同一账号换台机器看不到——真正的目录对象模型
  （钉盘 `local_id`/`parent_id` 树）是控制面的活，仍归后续切片。

### 切片 1 残余 — 写路径改走 fileId

- 新增 `drive.Client.DeleteByFileID`（服务端 `resolveDeletePath` 本就支持 fileId + 归属校验）；
- `spacedav.RemoveAll` 优先用列举结果里的 `fileId` 删除，取不到才退回路径；
- 理由：路径在「列出 → 删除」之间可能被别人改名占用，按身份删不会误伤他人的文件。
