### 一处**测试覆盖漏洞**（自查发现并补上）

`cfmount.Open` 是靠**类型断言** `cfg.Client.(Presigner)` 分流的：有预签名走 Range，
没有则退回整份读取。而生产用的 `*drive.Client` **有**预签名。

问题是：早先唯一的端到端假客户端**不实现** `Presigner`，于是
**端到端用例只覆盖了回退路径，而生产路径根本没被测到**。
功能测试全绿、但最重要的分支是盲区——这类漏洞比失败的测试更危险。

补法：两个假客户端并存，各自断言「建树零请求 + 读文件走的是预期分支」：

```
TestMountThroughAdapter       回退路径（无 Presigner）
TestMountThroughAdapterRange  Range 路径实测：[deep.txt bytes=0-17]（整份读取次数 0）
```

### 顺带修了**正在发布的那条路径**：`spacedav` 的 `Seek` 现在支持随机读

上一节发现 Range 可行的直接后果：`internal/spacedav`（**当前生产形态**，注册表 NameSpace
指 WebDAV UNC 那条路径）的 `readFile.Seek` 原本**只支持两种退化用法**，注释里写着
「真正的随机读需要 Range 请求，而控制面的预签名 URL 没有暴露该能力」。

**这句结论是错的**，代价不小——**视频拖动进度条、Office/PDF 打开大文件读尾部**
都依赖随机读，先前它们**一律失败**。

修法：抽 `internal/httprange`（与 cfmount 共用），`Seek` 改为
**向前跳丢弃字节 / 向后跳用 Range 重开流**；不支持预签名的客户端退回
「顺序读 + 向前跳」，向后跳仍返回 ErrInvalid（宁可失败，也不返回错位数据）。

**验证**（`internal/spacedav/seek_test.go`，5 个新用例，12 个既有用例全绿）：

```
TestSeekBackwardUsesRange  → 向后跳触发的 Range 请求: [bytes=5-19]
TestSeekForwardSkipsWithoutRange → 向前跳不发 Range（靠丢弃字节）
TestSeekEndAndCurrent / TestSeekNegativeRejected / TestSeekUnsupportedClientStillSequential
```

即：**向后跳真的只请求了 `bytes=5-19`**，不是整份下载；向前跳则完全不开新连接。

> ⚠️ 但**这一条当时只覆盖到 `readFile` 单元级**，没走真实 WebDAV handler。
> 补上外层测试后发现该结论**在端到端场景下不成立**（见下一节）。

> 这条修复影响的是**已经在跑的产品路径**，不再是原型。用户下次构建后，
> 从「此电脑」播放云盘视频应当可以拖动进度条。

### ✅ 最终结论：`spacedav` 的下载**此前完全不可用**，现已修复（KI-9）

上面那条「已回退」的叙述**已被后续证据取代**。回退之后我继续追查「为什么基线连
整份 GET 都失败」，拿到了决定性结果：

**基线状态下，从「此电脑」双击任何文件都返回 HTTP 500（`seeker can't seek`）——
不是拖进度条的问题，是全部下载都挂。**

根因：`readFile.Seek` 漏掉了 `http.ServeContent` 的**必需调用** `Seek(0, SeekStart)`。
ServeContent 的顺序与直觉相反——**先 Read(512) 探测类型，再 Seek(0) 回退重放**——
而旧实现只认 `(0, SeekCurrent)` 与 `(0, SeekEnd)`。

最小修复（保留，不复用那版复杂的窗口化实现）：`Seek(0, SeekStart)` 改为
**重开一条从 0 起的流**。实测结果：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 整份 GET | **500** | **200 且内容完整** |
| Range GET | 500 | **206 且区间精确**（顺带可用） |

详见 [`known-issues.md`](../known-issues.md) KI-9。
**本节的教训**：我在这条路径上先做了复杂方案（窗口化 + 惰性 reopen）并反复回归，
最后发现真正的最小修复只有几行——**复杂方案掩盖了「基线根本不能用」这个更基础的事实**。

### 附：紧随其后自查出的**性能缺陷**（该改动同样已随上面一并回退）

上一条修完后，我补了一条**走真实 `webdav.Handler`** 的端到端测试（此前只单测 `readFile.Seek`）。
它当场抓到：**一次 5 字节的 Range 读，对象存储却收到两次 `bytes=0-19`（整份）**。

根因是 `http.ServeContent` 的真实调用序列（用 trace 测试**测出来**，不是读源码猜的）：

```
Seek(0, Start) → Seek(0, End) → Seek(0, Start) → Seek(ra.start, Start) → Read
```

我的实现把每个「向后跳」都当成"立刻重开整份流"，于是中间两次 `Seek(0)` 各下一次整份。
**净效果比修改前更差**（原本只下一次整份）。

**修法：惰性 reopen**——`Seek` 只记目标位置（`pending`），真正开流推迟到 `Read`。
中间那些 Seek 全部零流量，只有实际要读时才发一个窄区间。

实测（`TestWebDAVRangeRequestThroughHandler`）：

```
修复前：对象存储侧 Range: [bytes=0-19 bytes=0-19]   ← 两次整份
修复后：对象存储侧 Range: [bytes=15-19]              ← 仅所需区间
```

**修复过程中又被测试抓到两个真问题**：

- `Close()` 在惰性设计下会 nil 解引用（`markPending` 关流后 body 为 nil）——**panic**
- `Seek` 对不支持预签名的客户端**不再立刻报错**（会拖到 Read 才失败）——
  惰性化不该以"静默延迟失败"为代价，已改回立刻报错

> 方法论：**单元测试全绿 ≠ 端到端对**。这条缺陷只有走真实 handler 才能发现；
> 而发现它的方式是**补一条更外层的测试**，不是再读一遍代码。

### 一条**被实测推翻**的既有结论（重要）

「同步回调会撞系统 I/O 超时」这句我早先写进了多处文档，但**从未实测**。
本轮把它变成可执行探测（`TestSyncFetchSlow`，延迟由 `CFAPI_SLOW_SEC` 配置）：

| 回调线程上睡 | 实测 |
| --- | --- |
| 5 秒 | ✅ 成功（5.017s） |
| 20 秒 | ✅ 成功（20.005s） |

**结论：20 秒以内没有观察到超时失败**，原强表述不成立，**已改写成更弱的表述**
（cfapi/README 的「已知局限」、cfmount/README 的缺陷 3、代码注释三处同步修正）。

仍成立的是两条更弱但确定的判断：
1. **回调线程被占住期间无法处理其他请求**（结构性，与超时无关）；
2. **等待时长没有已知上限**——只测到 20 秒安全，没探到阈值。

> 这条修正的**直接影响**：原先「必须改异步才能接真实云端」的结论不再成立。
> 接入时先跑一次大文件实测，据实测决定，而不是基于一个没验证过的担心。

### KI-8 先修：**Java 测试从来没有真正运行过**

起因是修复 KI-7 后想「把修复回退、看测试是否真的会失败」——结果**没失败**。
追下去发现父 POM（`platform/pom.xml:78`）设了 `maven.test.skip=true`，
于是：

```
[INFO] Not compiling test sources
[INFO] Tests are skipped.
[INFO] BUILD SUCCESS     ← 退出码 0，看起来"通过"
```

**50 个测试既没编译也没执行**。我的「43 个测试全绿」是假的（数还是从 `@Test` 计数来的，
与实际 50 个也不符）。修法：模块 POM 覆盖为 `false`。

修好后才看到**一条真实失败**：`restoreResetsToOrigin` 断言的是 `updateById`，
而实现早已改成 `update(null, LambdaUpdateWrapper)`——**测试与实现不符，因为测试从没跑过**。

### KI-7 后修：彻底删除会误删同路径的当前文件

对象键由路径派生（`DriveKeys.keyAt`），而「软删保留对象 + 重新上传覆盖同键」
会让回收站旧行指向的键**变成新文件的内容**。此时对旧行点「彻底删除」，
就会把用户**当前在用**的文件删掉。

修法最小且唯一：`purgeFromRecycle` 返回 `PurgeResult(row, deletable)`，
先查同路径 active 行；控制器据此决定要不要 `deleteAt`。
**行照常摘除（用户意图达成），对象只在安全时删。**

### 三条方法论（值得留下）

1. **"测试通过"要先确认测试真的跑了**。`mvn` 的 `skipTests` 默认会让 `BUILD SUCCESS` 撒谎。
   判据不是退出码，是输出里有没有 `Tests run: N`。
2. **回归测试必须验证「它能失败」**。我正是靠这一步才发现 KI-8——
   如果只跑一次「绿」就收工，两个缺陷都会留在产品里。
3. **`mvn test` 增量构建会给出陈旧结果**。本轮有两次「改了源码但结果不对」，
   都是没 `clean`。判断结论前先 `clean`。
