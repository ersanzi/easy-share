# 2026-10-21 · 会议纪要 skill 正文密度档（按宿主吞吐自动精简）

上一轮 [`2026-10-21-纪要skill长会实测复盘.md`](2026-10-21-纪要skill长会实测复盘.md) 把墙钟损失按项排完，
最大头是「三次长输出处方 ≈40 分钟」——**慢的从来不是输入，是输出**。用户据此提两条要求：
「减报告密度，精简但能突出重点」，以及「能不能自动化一点：宿主吞吐量不高就精简，吞吐高就可以详细」。
本轮就是这两条。

口径按用户选的**均衡档**收：单议题 1-2 个分节、每分节 1-2 组、每组 1-2 条 **≤45 字**、
`focus` 只 1 条、`insights` 0-1 条，单议题正文 200-400 字；**只收议题正文**，
`summary` 纪要 / 待办 / 关键词一个字不减（那是 docx 与 md 的骨架，砍它就是砍结论）。

## 实测依据

一次 59 分钟会的 summary 腿：**9604 字节 / 13.5 分钟 ≈ 12 字节/秒**（UTF-8 下一个中文字约 3 字节，
即约 4 字/秒）。这种吞吐下按详细档写 8 个议题，就是八条十分钟量级的腿并排烧。
而详细档单议题 800-1400 字里，真正是「重点」的部分（结论、数字、期限、责任人）在精简档里
一条都没丢——被砍的是过程叙述与发言复述。

## 设计决策

1. **两档提示词并存，不写「一个提示词 + 参数化长度」**（`engine/minutecraft/summarizer.py` ·
   `_TOPICS_SYSTEM_LEAN` / `_TOPIC_EXPAND_SYSTEM_LEAN`，`topics_request` / `topic_expand_request` 的
   `dense` 关键字参数）：篇幅口径与重点口径在一段话里互相牵扯，参数化容易改一处漏一处。
   两份的**不变量**由测试钉住而不是靠人读：`test_both_topics_prompts_keep_the_shared_invariants` /
   `test_both_expand_prompts_keep_the_shared_invariants` 断言两档共用同一 JSON 形状、`warm` 高亮、
   反引号数字、空标题禁令、「区间外不生成分节」，只有条数与句长不同。
   精简档第一版漏了 `group.title` 的口径（会退化成「讨论情况」这类空标题），就是这两条测试补上的。
2. **吞吐单位取「输出字节/秒」，不取 token/s**（`engine/minutecraft/engine.py` · `DENSITY_ENV`）：
   宿主能拿到的只有「回答文件字节数」和「这条腿花了多少秒」，token 数它测不准（各家分词器不同）。
   换算规则写进 `--output-bps` 的 help 与 SKILL.md，不让宿主自己除以 3 猜。
3. **阈值 `DENSITY_DETAILED_MIN_BPS` = 24 字节/秒**（≈8 字/秒）：高于它，详细档单议题 800-1400 字
   也就一两分钟，值得要详细；低于它，同一份正文把最慢一腿拖到十分钟以上。
   现场那次实测是 12 字节/秒，正好落在精简侧。
4. **`auto` 的判定顺序：显式指定 > 沿用 prepare 的显式指定 > 实测吞吐 > 材料规模**
   （`engine/minutecraft/engine.py` · `resolve_density`）。「沿用 prepare」这一条不是洁癖：
   `expand` 是另一次进程调用，如果它自己按规模重判，宿主在 `prepare --density detailed` 上的
   指定会在第二阶段悄悄变档，一场会出来两种版式。
   **吞吐同理**：prepare 把实测值记进 `plan.output_bps` 跟着请求包走，`expand` 沿用它——
   这条是 CLI 冒烟跑出来的真 bug（`prepare --output-bps 12` 判 concise，`expand` 却回说
   「宿主吞吐未知」按规模重判；反方向 `--output-bps 30` 的快宿主会被降档），
   由 `test_expand_reuses_the_throughput_reported_at_prepare` 钉住。扩写时重报更低的数则以新的为准
   （宿主中途换模型、并发被压下来都会改吞吐）。
5. **拿不到吞吐时按规模保守判，长会先精简**：规模阈值复用上一轮的
   `SPLIT_RECOMMEND_MIN_CHARS`（9000）/ `SPLIT_RECOMMEND_MIN_MINUTES`（35），不新造一个数。
   与上一轮「split-topics 只建议、不自动切」不同，这里**是**自动改默认路径——因为代价不对称：
   走错成精简档只是正文短些（重点口径一字不少），走错成详细档是多烧十几分钟墙钟。
6. **大纲腿与档位无关**（`topics_outline_request` 不接 `dense`）：它本来就不写正文，
   两条路的输出量一样，给它分档只会让人以为切分质量随档位变。
7. **判定结果与理由都顶到 `next`**（`engine/minutecraft/cli.py` · `cmd_prepare` / `cmd_expand`）：
   `[正文] concise 档：宿主实测 12 字节/秒 < 24…`。Agent 只照着 `next` 做，
   不写出来它就会在对话里自己催「写详细点」，把提示词收住的量又放出去。
   最终顺序是 `[建议]` 在 `[正文]` 之上——建议要重跑 `prepare`，比「这次写多长」更要命。
8. **出图侧一行没改**：`engine/minutecraft/render.py` · `build_report` 本来就是
   「`focus`/`insights` 有则用，没有就不画」。用裁剪过的样例真跑了一遍（见下表），
   不留空框、不塌版；议题间的空白带在详细档里同样存在，是分隔间距不是稀疏。
9. **`finish` 侧不新增校验**：少条数**不是漏答**。`test_finish_accepts_a_lean_topic_body_unchanged`
   钉住「精简档回答原样吃下、不出议题相关警告、不退回大纲」——否则 `exit 4` 会把宿主骗去重跑一条
   本来答得好好的腿。

## 兼容与迁移

- `plan` 新增 `density` / `density_reason` / `density_requested` / `output_bps` 是加法字段，旧调用方忽略即可；
  旧请求包继续能被 `finish` 接受。
- **有一处行为变化**：默认 `--density auto`，长会（压缩后 ≥9000 字或 ≥35 分钟）在宿主没报吞吐时
  从「详细」变成「精简」。这是本轮的意图，但**要固定口径就显式传 `--density detailed`**；
  无人值守的 `run` 路径完全不受影响（它走 `extract_topics`，仍是详细档）。
- 环境变量 `MINUTECRAFT_OUTPUT_BPS` 值非法时按「没给」处理，不会把链路搞挂。

## 实测后的下一步

1. 宿主拿一场 ≥40 分钟的会跑两档各一次，报三个数：总墙钟、最慢一腿秒数、人工抽查
   「精简档是否每条都是结论/数字/期限/责任人」。丢重点就把 `≤45 字` 放宽到 `≤60 字` 或
   每组允许 3 条，而不是把整档关掉。
2. 第二次实测若给出不同的吞吐临界点（不同模型、不同并发度），改 `DENSITY_DETAILED_MIN_BPS` 并回写本文件。
3. 若宿主普遍懒得传 `--output-bps`，考虑让 `expand` 自己估：`prepare` 落盘时间戳 + 大纲回答字节数
   能给出一个偏保守的下界。本轮没做，因为那条估算把「宿主读文件、起子代理」的开销也算进吞吐里，
   会系统性判低——宁可让宿主报一个真数。
