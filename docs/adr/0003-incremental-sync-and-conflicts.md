# ADR-0003：增量同步、游标与冲突语义

- 状态：提议
- 日期：2026-07-19
- 决策者：EasyShare maintainers
- 关联：[`0001-file-identity-and-version-model.md`](0001-file-identity-and-version-model.md)、[`0002-metadata-object-storage-consistency.md`](0002-metadata-object-storage-consistency.md)

## 背景

客户端会经历断网、睡眠、进程退出、消息重复和长时间离线。WebSocket 不能保证客户端永远在线，本地文件 watcher 也可能丢事件。如果只依赖实时通知或每次全量扫描，前者不可靠，后者在大量文件时成本不可接受。

双向同步还必须识别并发修改。静默采用“最后写入者获胜”可能永久覆盖用户内容，尤其是在两台离线设备同时编辑时。

## 决策

### 服务端变更日志

每个同步作用域维护有序 change journal。每次已提交的创建、内容更新、移动、重命名、删除、恢复和相关元数据变更都在数据库事务中写入一条或多条变更记录，并获得单调递增 sequence。

客户端通过分页接口拉取：

```http
GET /api/v1/changes?driveId=<id>&cursor=<opaque>&limit=500
```

响应至少包含：

```json
{
  "changes": [],
  "nextCursor": "opaque-token",
  "hasMore": false
}
```

cursor 对客户端是不透明值。客户端只在一页变更全部应用到本地 SQLite 后，原子保存 `nextCursor`。重复获取和重复应用必须安全。

WebSocket/SSE 仅发送“某作用域可能有新变化”的提示；断线后客户端直接从持久化 cursor 继续。游标历史若已过期，服务端返回专用错误和可审计的重新核对流程，而不是返回一个看似成功的空结果。

### 客户端本地变化

ReadDirectoryChangesW/fsnotify 事件只触发重新检查。客户端通过当前文件属性、已知 file ID 绑定和哈希策略确认真实变化，并定期执行范围核对，以弥补 watcher 溢出、进程离线和磁盘断开。

每个客户端操作携带：

- operation ID，用于幂等；
- device ID；
- 目标 file ID；
- 已知 entry revision；
- 内容更新时的 base version ID。

### 冲突规则

服务端当前状态与调用方 base/revision 不一致时，不静默覆盖。默认规则：

| 冲突 | 默认结果 |
| --- | --- |
| 内容修改 vs 内容修改 | 保留服务端当前版本，并创建可见冲突副本 |
| 删除 vs 内容修改 | 保留修改内容为冲突副本或恢复副本，不丢字节 |
| 重命名 vs 重命名 | 一个成功，另一个使用确定性冲突名称 |
| 目标目录同名 | 返回冲突并由同步引擎生成冲突名称后重试 |
| 移动到已删除目录 | 返回前提失败，不隐式移动到根目录 |
| 同一 operation 重试 | 返回第一次操作的结果，不创建额外副本 |

冲突名称必须稳定、可本地化并符合 Windows 文件名规则，例如：

```text
报告（冲突副本 - DESKTOP-ABC - 2026-07-19）.docx
```

具体名称格式是产品/UI 决策，但同一次冲突重试必须复用同一结果。

## 不变量

1. cursor 只在对应变更已事务性应用到本地状态后前进。
2. WebSocket、watcher 和轮询只能触发核对，不能代替事实来源。
3. 同一 operation ID 的重复请求不得产生重复副作用。
4. 无法证明操作基于当前版本时，不静默覆盖用户内容。
5. 删除也必须作为变更传播，并保留足够长的墓碑窗口。
6. 同步失败不会通过伪造成功 cursor 被跳过。

## 备选方案

### 每次启动全量列举并比较

不作为主方案。可作为修复和游标过期后的核对手段，但无法经济地支撑大目录和频繁同步。

### WebSocket 推送完整可靠事件

拒绝。客户端不可能保证持续连接，还需自行处理重放、顺序和断点，最终仍需要持久化日志。

### 按时间戳查询更新

拒绝。时钟、相同时间戳、事务提交顺序和删除记录都会造成遗漏。

### 最后写入者获胜

默认拒绝。实现简单但会静默丢失离线设备产生的内容。

## 影响

正面影响：

- 断网和重启后可可靠续传变更；
- 实时通知失效不会造成永久遗漏；
- 冲突结果可解释、可审计。

成本与风险：

- 服务端需要变更日志保留和压缩策略；
- 客户端应用变更必须事务化并支持幂等；
- 目录移动可能产生显示路径的大范围变化，但不应展开成所有后代内容变化。

## 开放问题

- change journal 按用户、drive 还是租户分区；
- cursor 保留期限和过期后的重新核对协议；
- 冲突副本归属原目录还是独立冲突区；
- 文档类文件是否未来支持应用级合并；
- 删除与修改冲突的确切 UI；
- 本地文件 identity 绑定使用 NTFS file ID、扩展属性还是 SQLite 路径映射的组合。

## 验证

至少覆盖：

- 两设备离线修改同一文件；
- 拉取一页后 Core 崩溃并重复应用；
- WebSocket 丢失、重复和乱序提示；
- watcher 缓冲区溢出后的周期核对；
- 目录移动与后代修改并发；
- 墓碑传播前后设备长时间离线；
- operation 请求超时后重试；
- cursor 过期时进入受控重建，而不是遗漏变更。
