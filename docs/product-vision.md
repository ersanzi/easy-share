# EasyShare 产品方向：网络云盘与内网协同

> 本文描述产品长期方向，不代表当前代码已经实现。当前可依赖能力以 [`architecture.md`](architecture.md) 为准，逐版交付情况以 [`iterations/`](iterations/README.md) 为准。推荐技术路线见 [`technical-selection.md`](technical-selection.md)，长期架构取舍见 [`adr/`](adr/README.md)。

## 1. 产品定位

EasyShare 的目标不是只把一个本地目录映射成网络盘，而是成为一个 **Windows 网络云盘客户端，同时保留和强化局域网能力**：

- 有网络时，用户登录账号后可以跨设备访问云端文件、查看容量、上传下载和同步文件夹。
- 同一局域网内，设备可以互相发现，并优先通过内网直传、同步或加速，减少公网流量。
- 在 Windows 资源管理器中提供稳定、可双击进入的 EasyShare 文件空间；应用界面负责账号、容量、传输、同步规则和设备管理。
- 断网时仍可访问已经本地化的内容，并在恢复网络后继续同步。

## 2. 目标用户体验

### Windows 资源管理器

最终入口应接近 WPS 云盘等成熟客户端，而不只是一个显示 `DavWWWRoot` 的 WebDAV 盘符：

- EasyShare 品牌名称和图标；
- 双击进入云端文件空间；
- 文件的同步中、已同步、仅云端、冲突、错误等状态；
- 右键上传、下载到本地、释放本地空间、复制分享链接等操作；
- 支持占位文件和按需下载，云端总容量可以大于本地磁盘可用空间；
- 用户选择的本地文件夹可以持续同步到云端。

账号 ID、套餐/容量、传输队列、上传入口、同步文件夹和设备列表应在 EasyShare 主界面中有明确页面；资源管理器可以提供快捷入口和文件状态，但不应把所有管理 UI 伪装成普通文件。

### EasyShare 主界面

建议的信息架构：

1. **云盘**：最近文件、上传、容量与云端状态；
2. **传输**：上传、下载、内网直传、失败重试和历史记录；
3. **同步文件夹**：选择本地目录、同步方向、暂停和冲突处理；
4. **附近设备**：内网设备、发送文件、可信设备和传输速度；
5. **账户与设置**：用户 ID、空间用量、安全、网络策略和缓存上限。

## 3. 技术方向

### 3.1 Windows 文件系统集成

当前 WebDAV 网络驱动器适合验证文件访问和生命周期，但不足以实现成熟云盘体验。正式云盘入口优先评估 Windows Cloud Files API（CfAPI）与 Sync Root：

- 资源管理器原生占位文件；
- 文件按需水合/回收；
- 同步状态与进度；
- 自定义同步根名称、图标和上下文菜单；
- 离线缓存和选择性同步。

Shell 扩展必须控制在最小范围，避免拖慢或崩溃 `explorer.exe`。资源管理器集成进程与 Go Core 之间应使用版本化的本机协议，而不是让 Shell 代码直接操作云端数据库。

### 3.2 云端控制面与数据面

云端至少需要：

- 账号登录、设备会话、Token 刷新与撤销；
- 用户、设备、文件元数据、目录树、版本、回收站和配额；
- 分片上传、断点续传、完整性校验和秒传/去重策略；
- 对象存储中的文件内容；
- 分享、权限和审计；
- 服务端通知或增量游标，避免每次全量扫描。

文件内容和元数据需要明确的一致性模型。客户端必须使用稳定的文件 ID，而不能只依赖会变化的路径。

### 3.3 同步引擎

同步引擎需要独立于 UI，继续运行于 Core：

- 本地文件变更监听与云端增量拉取；
- 上传/下载任务持久化，重启后恢复；
- 分片、校验、限速、暂停、重试和退避；
- 重命名、移动、删除和大小写差异处理；
- 冲突副本规则，绝不能静默覆盖无法判定的新版本；
- 可配置缓存与“始终保留在此设备”。

### 3.4 内网能力

内网不是云端功能的旁路，而是同一文件身份体系下的传输优化和独立能力：

- 同账号设备或已配对可信设备之间直传；
- 云端已经确认目标版本时，可从附近设备获取相同内容并做哈希校验；
- 公网不可用时仍允许显式的局域网发送与接收；
- 支持策略选择：优先内网、仅内网、允许公网回退；
- 设备认证、加密和权限判断不能继续假设局域网天然可信。

## 4. 分阶段路线

### 阶段 0：Windows 本地入口可用（当前迭代）

- 启动桌面端后自动连接现有 WebDAV 网络盘；
- 安全复用 EasyShare 自身映射；
- 双击标准网络驱动器进入；
- 继续验证 Core 生命周期、日志和 Windows WebClient 兼容性。

### 阶段 1：云端 MVP

- 账号与设备登录；
- 文件元数据 API、对象存储和用户配额；
- 应用内上传、下载、目录浏览和持久化传输任务；
- 暂时可使用普通本地同步目录，不立即开发复杂 Shell 扩展。

### 阶段 2：同步文件夹

- 本地目录监听、云端增量游标、双向同步和冲突处理；
- 断点续传、缓存管理、暂停/恢复和传输历史；
- 双机、断网、重启和大文件验收。

### 阶段 3：WPS 式系统原生入口（Windows CfAPI / macOS FileProvider）

同一目标在两个平台的对等实现，可共享同步引擎设计：

- **Windows**：CfAPI Sync Root、占位文件和按需下载；品牌图标、同步状态、右键菜单与选择性离线；安装器负责注册、升级、回滚和卸载清理；对 `explorer.exe` 稳定性、性能和兼容性做独立发布门禁。
- **macOS**：FileProvider 扩展（App Extension，跑在系统 `fileproviderd`），让 EasyShare 作为带品牌图标的位置出现在 Finder 侧边栏，支持占位文件、按需下载、同步状态角标、Finder 内增删改自动同步。这是 macOS 上「此电脑」的真正对等方案，取代 mac-ready 阶段临时的 WebDAV 挂载。
- **macOS 投入说明**：FileProvider 须用 Swift/Objective-C 编写独立扩展、Xcode 构建、Apple 开发者账号签名公证，是独立于 Go/Vue 栈的技术投入，工作量与 Windows CfAPI 相当。详见 [`macos-port.md`](macos-port.md)。

### 阶段 4：云端与内网融合

- 可信设备配对和端到端加密；
- 同一内容优先从局域网设备获取；
- 内网发送转为可进入云盘/同步目录的统一任务；
- 网络切换、离线与公网回退策略。

## 5. 当前架构应保留的演进空间

- UI 不直接依赖 WebDAV；文件入口只是 Core 提供的一种能力。
- 传输任务模型后续要能统一表示上传、下载、同步和局域网直传。
- 文件记录后续使用稳定 ID、版本和内容哈希，不把绝对本地路径当作云端身份。
- Core API 继续只监听本机并版本化；云端凭据不得暴露给前端或 Shell 扩展。
- 当前 `DriveMapped` 状态不要扩展成所有云盘状态的总开关；未来应拆分本机入口、云端会话、同步引擎和网络健康状态。

## 6. 已确认和待决策

已经确认：中国大陆首发，对象存储自行建设，RustFS 为首选实现并受 [`ADR-0006`](adr/0006-rustfs-self-hosted-object-storage.md) 的生产门禁约束。进入云端 MVP 前仍须明确：

- 服务面向个人、家庭还是团队；
- 免费额度、单文件上限和成本预算；
- 分享和协作权限范围；
- 是否要求端到端加密，以及服务端是否需要内容去重/预览；
- 同步冲突、删除保留期和版本历史策略；
- 第一版是否必须提供 CfAPI，还是先通过应用内云盘和普通同步目录验证需求。
