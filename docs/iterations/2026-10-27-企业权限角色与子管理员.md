# EasyShare 企业权限 · 角色组与子管理员

> 承接[第二轮功能权限矩阵](2026-10-27-桌面端企业化整改-第二轮.md)。用户提出「权限做好了吗 要像钉钉这样精细化」，在三层精细化路线里选定先做第一层：**角色/权限组 + 子管理员**。
> 下一片是数据权限范围（self/dept/dept+children/specified/all），第三片是文档级成员角色。

## 用户问题

用户原话：「权限做好了吗 要像钉钉这样精细化」。

上一轮的矩阵是**逐账号开关**：几十上百人时要一个个点，且没有「谁能管理权限」这一层——只有 RuoYi 超管能进管理页，部门主管无法自助管本部门。钉钉的对应能力是「角色/权限组」与「子管理员」。

## 目标

1. **角色/权限组**：把五项功能开关打包成角色，成员挂角色后按角色生效；多个角色取并集。
2. **子管理员**：角色可标记 `admin_scope=dept`，挂了该角色的成员能进管理页，但**只看到、只修改本部门成员**。
3. 保留逐账号矩阵：没有角色的成员沿用「缺行 = 五项全开」，存量账号零迁移。

## 非目标

- **数据权限范围**（自己/本部门/本部门及下级/指定部门/全部）——下一片，会复用本轮的子管理员范围骨架。
- **文档级成员角色**（管理/可编辑/只读，是否可下载、复制、外链）——第三片。
- **操作审计**（谁改了谁的权限）——用户本轮未选。
- 部门树递归：本轮子管理员范围是 `sys_user.dept_id` **精确匹配**，不含下级部门；规则一句话能说清，递归留给数据权限片。

## 设计决策

### 1. 裁决顺序：角色并集 > 逐账号行 > 全开

新增两张表（`deploy/ruoyi-db/easyshare-permission-role.sql`）：

- `es_permission_role`：`role_id`、全局唯一的 `role_name`、`admin_scope`（none/dept）与五项开关。
- `es_user_role`：`(user_id, role_id)` 复合主键的多对多绑定。

生效权限的裁决顺序固定在 `FeaturePermissionService.effective`：

1. 账号有角色 → 五项取所挂角色的**并集**，逐账号行不再参与；
2. 没有角色 → 读 `es_user_permission` 逐账号行；
3. 也没有行 → 五项全开（与上一轮完全一致）。

把规则收在一个静态方法里，`/mine`、管理页成员列表、`enabled` 三处共用，避免「列表显示的值」和「实际拦截的值」分叉。`drive` 关闭时 `shared` 一并失效的口径不变，对角色并集同样适用。

### 2. 删角色先落快照，避免「删角色 = 全开」

如果只删角色与绑定，单角色成员会变成「无角色且缺行」，按规则 3 被放大成五项全开——管理员的直觉是「删角色 = 收回这批人的统一配置」，不该顺手把限制也删了。

`PermissionRoleService.delete` 在解绑后，对**只剩这一个角色**的成员把角色开关落成一行 `es_user_permission` 快照；还有其他角色的成员直接跳过（他们的权限仍由剩余角色决定）。逐账号行在挂角色期间不删除，移除全部角色后自然回到挂角色之前的配置。

### 3. 子管理员范围在服务端裁剪，不借 RuoYi 的用户列表权限

RuoYi 的 `/system/user/list` 要求 `system:user:list`，普通子管理员没有；若直接复用，要么把子管理员挡在门外，要么被迫给他全局用户列表权限——两种都不对。

新增 `GET /easyshare/permission/admin/members`，由 `PermissionRoleService.membersOf` 按操作者范围裁剪：超管拿全部成员，`dept` 子管理员只拿 `dept_id` 精确相等的成员。写接口 `PUT /easyshare/permission/admin` 用 `canManage` 做同样的校验。

**没有部门的账号拿不到 `dept` 范围**（`adminScopeOf` 返回 none）：范围无法界定，宁可不给管理入口，也不能退化成「所有人可见」。

### 4. 角色定义与分配只有超管能改

角色是跨部门的；如果允许子管理员编辑角色或给成员挂角色，他就能给自己挂一个权限更高的角色完成越权。因此：

- `/admin/roles`（增删改）、`/admin/members/{userId}/roles`（分配）全部 `@SaCheckRole("superadmin")`；
- 子管理员只能改本部门成员的**逐账号开关**，且目标成员挂了角色时服务端直接拒绝——角色优先，写逐账号行不会生效，静默成功会误导管理员。

### 5. `/mine` 扩展保持向后兼容

`GET /easyshare/permission/mine` 在原有五项扁平布尔之外增加 `adminScope` 与 `roles`（角色名数组），**不做嵌套**：知识服务 `_feature_flags` 与 Go `FeatureFlags` 的既有解析不需要改动。Go 侧用 `account.MyPermission` 内嵌 `FeatureFlags` 承接。

### 6. 桌面端：入口放开给子管理员，角色编辑只读给非超管

- `AuthUser` 增加 `adminScope`（all/dept/none/空）；空串表示未知（旧控制面或拉取失败），入口沿用 `isAdmin`，不会误把老用户挡在门外。
- `App.vue` 的 `canAdmin = isAdmin || adminScope === 'dept'`，侧栏「管理」入口与页面渲染同口径；失去管理范围时若正停在管理页则退回工作台。
- 管理页：账号/空间/概览三个 Tab 仅超管可见；权限 Tab 所有管理员可见。超管看到角色管理卡与成员矩阵的角色勾选菜单；子管理员只看到本部门成员、角色名静态展示、五个开关可改。
- 成员挂了角色时，开关在界面上禁用并显示「由角色决定」；改角色后桌面壳调用 `refreshOwnPermission` 刷新自己的入口（管理员可能把角色挂到自己头上）。

## 兼容与迁移

- 新 DDL 幂等（`CREATE TABLE IF NOT EXISTS`），已加入 `scripts/ship-control-plane.ps1` 的 `$easyshareSql`，每次投递重放。

## 已知边界与后续切片

1. **子管理员范围不含下级部门**：只匹配 `sys_user.dept_id` 精确相等。下一片「数据权限范围」会把可见范围升级成 self/dept/dept+children/specified/all，子管理员可继承同一套范围表达式。
2. **角色是全局的，不按部门隔离**：任何部门都可以挂任何角色；如需「研发部只能看到研发部角色」，需要给角色加归属部门，属于数据权限片之后的细化。
3. **删除角色只给单角色成员落快照**：多角色成员由剩余角色继续裁决；历史上挂角色前的逐账号行一直保留，移除全部角色后会恢复该配置（刻意如此，不是「重置为全开」）。
4. **文档级 ACL 不变**：仍由 `es_file.visible_depts` 控制，角色不影响文档可见性——这正是第三片要补齐的「文档级成员角色」。
5. **操作审计未做**：谁给谁挂了什么角色、谁改了什么开关，目前只有应用日志，没有可查询的审计表。
6. **在线成员的入口显隐会滞后**：角色变更后，服务端拦截立即生效，但其他已登录客户端要等下一次启动校验或手动刷新资料才更新入口——与上一轮矩阵的行为一致，没有主动推送通道。

## 真机点验清单（下次省事）

本轮需要控制面重部署（含新 DDL）+ 桌面端重装才能端到端可见：

1. 超管建角色「车间只读」只开知识问答，把 A 挂上 → A 的五项开关在矩阵里只读，生效值是「知识开、其余关」；A 退出重登后仍按角色生效。
2. 再建角色「例会成员」只开会听记，同样挂给 A → A 生效为「知识 + 会议」并集。
3. 把 B 的部门设好，给 B 挂「子管理员 · 本部门」角色 → B 侧栏出现「管理」，进来只有「权限」页签，成员列表只含本部门；改其他部门成员应被服务端拒绝。
4. 子管理员直接请求 `/easyshare/permission/admin/roles` → 403。
5. 移除 A 全部角色 → A 回到挂角色之前的逐账号配置（不是五项全开）。
6. 删除「车间只读」→ 只挂过它的成员的权限保持删除前的值（已落快照），不会被放大成全开。
7. 超管在矩阵里给挂了角色的成员改开关 → 开关禁用；若绕过 UI 直接调 `PUT /easyshare/permission/admin` → 返回「该成员的功能权限由角色决定」。
