## 🔴 抓到一个真实生产缺陷：增量列举把视图塌掉

### 症状

`TestLiveSpacedavRoundTrip` 报「删除后列表里仍有该文件」，但数据库里两条记录都对。
第二次刷新才消失。

### 根因（诊断打印出来的）

```
RemoveAll key= live-spacedav/renamed-1792213394316873400.txt  cacheSize= 0  targets= 0
```

`cacheSize=0` —— `f.objects()` 走了**增量路径**，而内存缓存 `base` 是空的。

`spacedav` 的原判据是「磁盘上有 lastVersion 就走增量」：

```go
if since > 0 { sincePtr = &since }   // ❌ 错了
```

而增量流**只描述差异**。`base` 为空时 `merged` 从空开始，变更集里只有本次那一条，
**其余对象全部从视图里消失**。

### 为什么症状是「删不掉」而不是报错

`RemoveAll` 拿 `targets`（从空视图算出来）→ 长度 0 → 打的是「只是个空目录，无对象可删」这条分支 →
**return nil**。调用方以为删成功了。

同一坑还有另一张脸：任何「写后 invalidate + 马上列举」的操作都会看到空/残缺列表。

### 修法

```go
if since > 0 && base != nil { sincePtr = &since }   // ✅ 有底才走增量
```

**没有底就退回全量**——这是「增量只描述差异」的直接推论。

### 回归测试先验证「它能失败」

`TestFSUsesDiskVersionAcrossRestart` 原先断言的正是「重启后用增量拼出完整列表」——
**那个断言本身是错的**，它靠假客户端伪造一个包含全部对象的变更集才「通过」。
改成断言**请求形态**（`lastSince == nil` 即走全量）后：

| | 结果 |
| --- | --- |
| 修复后 | ✅ PASS |
| 把判据改回 `since > 0` | ❌ FAIL：「应发全量请求，实发 10」 |

这正是文档里反复强调的那条：**回归测试必须验证它能失败**。
