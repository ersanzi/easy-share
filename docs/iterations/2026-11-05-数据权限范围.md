# EasyShare 企业权限 · 数据权限范围（管理范围表达式化）

> 承接[角色/权限组与子管理员](2026-10-27-企业权限角色与子管理员.md)声明的下一片：把子管理员的管理范围从「本部门精确匹配」升级为范围表达式（本部门 / 本部门及下级 / 指定部门 / 全部成员），表达式挂在角色上，与钉钉「子管理员管辖部门」、RuoYi `sys_role.data_scope` 对齐。

## 用户问题

上一片留下的已知边界第一条：「子管理员范围不含下级部门：只匹配 `sys_user.dept_id` 精确相等」。企业组织是树——集团→子公司→部门→车间，只管本部门一层管不到下级车间的成员，子管理员能力在实践中形同虚设。

## 目标

1. `es_permission_role.admin_scope` 扩展为五档：`none` / `dept`（本部门）/ `dept_children`（本部门及下级）/ `specified`（指定部门列表）/ `all`（全部成员）。
2. `specified` 档的范围部门列表存角色新列 `scope_dept_ids`，超管建角色时从部门树勾选。
3. 多个管理角色取并集；功能开关裁决、删角色快照等既有语义一律不变。
4. 管理页成员矩阵与写接口（`canManage`）按同一套范围表达式裁剪——「列表显示的值」和「实际拦截的值」不分叉。

## 非目标

- **self 档不做**：RuoYi 的 self 是数据可见性场景（只看自己的单据）；子管理员管理场景里「只能管理自己的功能开关」没有真实需求，多一档只增加理解成本。
- **数据可见性不变**：文档级可见性仍由 `es_file.visible_depts` 与知识服务 `visible_depts` 承担（第三片「文档级成员角色」再统一）。
- **部门树递归解析在内存做**：企业部门数量级（几百以内）不值得引入 ancestors 递归 SQL 或闭包表；`sys_dept.parent_id` 内存 BFS 即可，存量库零升级成本。

## 设计决策

### 1. 范围表达式挂在角色上，不另立表

子管理员身份本来就来自角色（`admin_scope != 'none'`），范围表达式是同一件事的细化——把 `admin_scope` 的值域从 `{none, dept}` 扩成 `{none, dept, dept_children, specified, all}`，加一列 `scope_dept_ids TEXT`（逗号分隔 `sys_dept.dept_id`）承接 specified。DDL 对存量库幂等（`ADD COLUMN IF NOT EXISTS`），纳入 ship 脚本自动重放。

字段名沿用 `adminScope`：桌面端 wire 值同步扩展，旧值 `dept` 语义不变（超集兼容）。

### 2. 范围解析收口在一个方法，三处共用

`PermissionRoleService.rangeOf(actorId)` 返回解析结果（全部 / 部门集合），`adminScopeOf`（`/mine` 的入口显隐）、`canManage`（写校验）、`membersOf`（矩阵裁剪）三处共用：

- 超管 → 全部；
- 逐个取角色：`dept` 需要本人有部门（否则该角色不生效，继续看其余角色）；`dept_children` = 本人部门 + `sys_dept.parent_id` 内存 BFS 后代；`specified` = 解析 `scope_dept_ids`；`all` 直接全部；
- 多角色取并集；全部角色都不生效 → 无管理入口。

与上一片一致的两条红线保留：没有部门的账号挂 `dept`/`dept_children` 角色不生效（范围无法界定宁可不给）；`/mine` 拿不到范围时前端按 `isAdmin` 走老路径（空串=未知）。

### 3. wire 返回真实档位，前端按「非 none」判入口

`/mine` 的 `adminScope` 从三值 `{all, dept, none}` 扩为真实档位（`dept_children` / `specified` / `all`…）。桌面端这批代码尚未发版（0.5.2 于 10-13 发布，权限矩阵是本批未提交工作），wire 无存量兼容包袱——返回真实档位让管理页徽标能显示「子管理员 · 本部门及下级」。前端入口判定从 `adminScope === 'dept'` 改为「非 none 且非空」。

### 4. 角色定义与部门勾选仍只有超管

`specified` 的部门列表在角色上，与「角色是全局的」既有决策一致：子管理员仍然只能改本范围内成员的逐账号开关，不能碰角色定义。`/admin/depts`（部门下拉）本来就是 `@SaCheckRole("superadmin")`，角色编辑卡复用。

### 5. 功能开关裁决零改动

`FeaturePermissionService.effective` 只消费角色的五项开关，与 `admin_scope` 档位无关；本片不碰知识服务与 Go 侧权限解析（`MyPermission` 的 `adminScope` 是 string 透传）。

## 兼容与迁移

- 新列 `scope_dept_ids` 幂等补列；存量 `dept` 角色行为与升级前完全一致。
- 旧值域 `none`/`dept` 是新值域的子集；已落库的角色无需迁移。
- 桌面端与 Core 同包发布，不存在「旧 Core + 新前端」组合。

## 真机点验清单（下次省事）

1. 超管建角色「华东大区管理」，范围选「本部门及下级」，挂给华东负责人 C → C 进管理页可见华东大区部门及其子部门的全部成员，改其中任何人的开关成功；改华北成员被服务端拒绝。
2. 建角色「质检组管理」，范围选「指定部门」勾选质检部，挂给 D（D 属于研发部）→ D 可见并管理质检部成员（范围在角色上，与 D 本人部门无关）。
3. 建角色「全局协管」，范围选「全部成员」，挂给 E → E 进管理页可见全公司成员；`/easyshare/permission/admin/roles` 仍 403（角色定义只有超管）。
4. 把 C 挂「华东大区管理」+「质检组管理」两个管理角色 → 可见范围为两档并集。
5. 无部门的账号挂「本部门及下级」角色 → 不出现管理入口（范围无法界定）。
6. 旧「本部门」角色行为不变：只看到 `sys_user.dept_id` 精确相等的成员。
