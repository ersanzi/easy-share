# 空间池上限、呈现差异与整理算法 — 详细方案

日期：2026-08-30
状态：待实施（按序号推进，每项独立可验收）

## 背景与当前缺口

配额模型已落地（见 ADR-0007「空间授权与配额」一节），但只有**逐空间上限**，
没有**总量概念**。实测数字暴露问题：

| 观测点 | 容量 |
| --- | --- |
| 容器内 `df /data` | 1007 GB（可用 953 GB） |
| **宿主 D 盘真实可用** | **123 GB** |

容器那个 953 GB 是 WSL2 稀疏 vhdx 的虚数，真实天花板是宿主 D 盘。
`SpaceService.assertFits` 只比「该空间已用 + 本次 > 该空间配额」，
**不看物理容量、不看已承诺总量**。

后果：可以给 20 个账号各分 100 GB，系统全部接受；写到 123 GB 时 RustFS 报存储错误。
**用户看到的是「配额还剩 80 GB」但传不上去** —— 配额数字变成谎言，这是最糟的失败模式。

## 1. 池上限与物理容量感知

### 设计

不改成纯池化。**逐空间配额 + 池上限两层并存**：
逐空间配额挡「一个人吃光」，池上限挡「超过物理盘」。只有其一都不完整。

**允许超配，但必须可见。** 承诺 200 GB 而物理 123 GB 是云盘常态（大多数账号用不满），
禁止超配会浪费容量。要的不是禁止，是让管理员看得见比例、并在真的写不下时给出
**正确的错误信息**。

### 数据来源

物理容量不落库，实时探测——它会随宿主磁盘变化，存下来必然过时：

- RustFS 部署在容器里，`df` 看到的是 vhdx 虚数，**不可用**
- 真值要问宿主。控制面自己也跑在宿主上，故用 Java 的
  `FileStore.getUsableSpace()` 探测 **Docker 数据根所在卷**
- Docker 数据根从 `docker info` 的 `DockerRootDir` 得到；本机在 D 盘
- 新增配置 `easyshare.drive.capacity-path`，默认留空表示不启用池上限
  （未配置时行为与现在完全一致，不引入回归）

### 判定

`presign-put` 现有判定之后再加一道：

```
承诺总量 = Σ(所有 quota_bytes > 0 的空间配额)
实际总用量 = 全桶用量（已有 sumBytesGrouped 可复用）
池剩余 = 物理可用 - 预留水位
若 实际总用量 + size > 池剩余 → 拒绝
```

**预留水位**：新增 `easyshare.drive.reserved-bytes`，默认 5 GB。
磁盘写满会影响 PG/Redis/系统本身，不能让云盘吃到 0。

### 错误信息必须分得清

这是本项做出来的主要价值。两种"满"的应对方式完全不同：

- 「你的空间已满（已用 9.8 GB / 10 GB）」→ 用户自己删文件
- 「服务器存储不足，请联系管理员」→ 用户删自己的文件没用

现在只有前者。混在一起会让用户白忙。

### 管理页

空间页顶部加一行容量总览：

```
物理可用 123 GB   已承诺 60 GB (49%)   实际已用 0 B
```

超配时（已承诺 > 物理可用）显示警告色与说明，**不阻止保存**——
管理员应当能有意超配。

### 落点

- `DriveProperties`：`capacityPath`、`reservedBytes`
- 新增 `CapacityService`：探测物理可用（缓存 60 秒，`df` 不便宜）
- `SpaceService.assertFits`：加池判定，错误信息区分两种满
- `SpaceController`：`/admin/capacity` 返回总览
- Go：`Capacity()` 透传 + Wails 方法；管理页顶部总览

### 验收

1. 配置一个极小的 `reserved-bytes`（如物理可用 - 1 MB），上传应被拒且错误信息是「服务器存储不足」
2. 恢复正常配置，同样的上传应通过
3. 未配置 `capacity-path` 时行为与本项实施前一致
4. 管理页超配时显示警告，且仍能保存

## 2. 共享盘对管理员/普通用户的呈现差异

### 设计

同一个共享空间，两种视图。差异**只在呈现**，不在授权——授权始终由
`es_space_member` 决定。

| | 普通成员 | 管理员 |
| --- | --- | --- |
| 「此电脑」副标题 | `已用 12 GB / 50 GB` | 同左 |
| 客户端共享空间页 | 只看总量与自己传的文件 | 额外看**按成员分组的用量** + 成员列表 |
| 文件列表 | 全部可见（共享空间的语义） | 同左，另显示每个文件的上传者 |

**为什么普通成员也看总量**：共享空间是公共资源，成员需要知道还剩多少才好决定传不传。
藏起来只会让人反复试。

**为什么只有管理员看分组用量**：「谁占了多少」在小团队里是敏感信息，
且普通成员看了也无权处置。

### 需要补的数据

现在 `shared/` 下的对象**不记上传者**。要显示上传者与分组用量，得让键或元数据带上它。
两个选择：

- **A. 键里带**：`shared/{userId}/相对路径`。分组用量直接从前缀聚合，零额外成本。
  代价是同一个文件换人传会出现在不同前缀下，且"共享空间是一个平坦空间"的语义被打破。
- **B. 对象元数据带**：`x-amz-meta-uploader`。语义干净，但聚合要逐对象读元数据，
  列举时拿不到，成本高。

**倾向 A**，理由是聚合成本决定了功能可用性；且共享空间里按人分目录本身也符合直觉
（类似「各自的收件箱」）。但这改动会改键结构，**必须在写入真实数据前定**。

### 落点

- `DriveKeys`：`sharedPrefix()` 改为 `sharedPrefix(userId)`（与第 5 项合并做）
- `SpaceController`：`/admin/shared-usage` 返回按成员分组
- 管理页共享空间区：成员用量列表
- 客户端共享空间页：按 `isAdmin` 分两种呈现

### 验收

1. 普通账号登录：看到总量，看不到分组用量（接口也要拒，不能只靠前端隐藏）
2. 管理员登录：看到分组用量，数字与 `sumBytesGrouped` 一致
3. 撤销某成员授权后，其分组用量仍在（文件还在），但该成员看不到这个空间

## 3. 非管理员账号的实机验收

**这项优先级被低估了。** 目前全部验证（24 项）都是 admin 跑的，
而 admin 拥有 `*:*:*` 通配权限，是**证明力最弱**的账号——它能过不代表隔离成立。

### 步骤

1. 建普通账号 `alice`（管理页新建，不给任何角色）
2. 用 alice 登录客户端，验证：
   - 管理入口**不显示**
   - 直接调 `/easyshare/space/admin/*` 被 Sa-Token 拒（**这条最关键**：
     前端隐藏是障眼法，真正的门在控制面）
   - 未分配配额时「文件」页显示「待开空间」，上传被拒
   - 管理员给 alice 分 1 GB 后，alice 能传，超 1 GB 被拒
   - alice 看不到 admin 的文件（`users/{aliceId}/` 与 `users/{adminId}/` 隔离）
   - 未授权共享空间时，alice 的「此电脑」里没有共享盘
3. 把这些固化成脚本 `scripts/verify-tenant-isolation.py`，
   与 `verify-space-quota.py` 并列

### 验收

脚本全绿，且**至少有一项断言是"alice 调管理接口应失败"**——
没有这条，等于没验证鉴权。

## 4. 整理算法

### 参考与边界

DeskBox 是 **GPL-3.0**：只借架构思路，**绝不移植代码**，也不复制其规则表。
参考的是「分层归类」这个结构，不是它的实现。

### 分层设计

整理不是单一规则，是一条**优先级链**，先命中先归类：

1. **显式规则**（用户自定义）：扩展名 / 文件名正则 → 目标目录。最高优先级，
   用户说了算。
2. **类型层**：按扩展名归大类——文档 / 图片 / 音视频 / 压缩包 / 安装包 / 代码。
   这一层覆盖绝大多数文件。
3. **时间层**：类型层内再按 `年/月` 分。仅当该类文件数超阈值（如 50）才启用，
   否则一个月一个空目录反而更乱。
4. **兜底**：`其他/`。**必须有**——归不了类的文件不能留在根目录，
   也不能凭猜硬塞进某一类。

### 关键约束

- **只动云端键，不动本地文件**。整理是重命名对象键（复制 + 删除），
  用户本地目录不受影响。
- **必须可预览、可撤销**。先出「变更清单」让用户确认，执行时记录
  `原键 → 新键` 映射，撤销就是反向执行。没有这个不敢让它自动跑。
- **冲突不覆盖**。目标键已存在时加后缀 `(2)`，绝不覆盖——
  覆盖会静默丢数据。
- **配额中性**。整理只改键不改字节数，总用量不变；但复制阶段会短暂占双份，
  配额判定要考虑这一点（或用服务端 copy 避免）。

### 落点

- `platform-drive`：`OrganizeService`（规则链 + 预览 + 执行 + 撤销）
- 规则表落库 `es_organize_rule`，或先硬编码类型层、显式规则后置
- 客户端：整理页（预览清单 + 确认 + 撤销入口）

### 验收

1. 预览清单与实际执行结果一致（不能预览一套、执行另一套）
2. 冲突时加后缀，原文件仍在
3. 撤销后键完全回到原状
4. 整理前后总用量不变

## 5. 共享空间从单例改成带 spaceId 的前缀

**趁桶还空着做，成本为零。** 现在 `shared/` 是全局单例（`space_id = 1` 由 DDL 预置），
`es_space` 表本身支持 N 行共享空间，只有 `DriveKeys.sharedPrefix()` 与那个常量把它锁成一个。

一旦 `shared/` 下有了真实对象，改前缀就不只是改代码——要搬对象存储里的数据。

### 与第 2 项合并

第 2 项若采纳方案 A（键里带 userId），前缀会变成
`shared/{spaceId}/{userId}/相对路径`。两项一起改，只动一次键结构。

### 落点

- `DriveKeys.sharedPrefix(spaceId, userId)`
- 去掉 `EsSpace.SHARED_SPACE_ID` 常量的特殊地位
- `SpaceService` 的共享相关方法收 `spaceId`
- 客户端：`space` 参数从 `"shared"` 变成 `"shared:{spaceId}"` 或独立字段

### 验收

1. 现有单个共享空间行为不变
2. 手工插入第二行共享空间，两者的对象互不可见
3. 成员授权按 spaceId 独立生效

## 未决问题（需产品决定，不由实施者定）

1. **配额是硬约束还是运营指标。** 现状是指标：客户端申报 size 可少报，
   并发签发也能绕过（多个 URL 各自看到旧的已用量）。变硬约束要放弃直传、
   走控制面代理，性能代价明确。
2. **超配是否允许。** 本方案默认允许并显示警告。禁止则简单但浪费容量。
3. **共享空间是否按人分目录**（第 2 项的 A/B 选择）。影响键结构，越早定越好。

## 后续（本方案之外）

- 服务器部署：数据主要放服务器，本机客户端对接。凭据已提供，
  等本地这几项落地、真要部署时再动。届时要处理的是：控制面与 RustFS 的公网暴露面、
  凭据管理（不能再用 dev 的明文 .env）、以及客户端的服务地址配置。
