## 1. 结论先行：它们漂亮在哪

不是"配色好看"，而是**五条可量化的工程规律**：

1. **颜色是算出来的，不是挑出来的** —— 12 色系 × 10 阶，同一色系 H 恒定，明度按固定节奏递减。
2. **中性色注入品牌色相** —— 灰不是灰度，是 `H≈220°` 的蓝灰，且越浅越去饱和（31%→14%）。
3. **品牌色降饱和** —— WPS 主色 `S=76%`，不是 100%。满饱和蓝在大屏上会刺眼。
4. **状态是相邻阶** —— hover 取浅一阶、pressed 取深一阶，不另造颜色。
5. **留白按 4 的倍数膨胀** —— 列表行高 64px 配 14px 字，一条行里塞 4.5 倍行高的呼吸空间。

## 2. WPS 的 KD（金设计）体系

### 2.1 三层结构

```
① 原始色板   kd-color-{hue}-1 … -10     12 色系 × 10 阶，纯数值
                    ↓ 引用
② 语义层     CommonThemePalette          kd-color-{角色}-{变体}
                    ↓ 引用
③ 组件层     KSearchPanel / KToast …     每个控件只写语义名，不写色值
```

实测：`kd-color-text-primary` 在组件里被引用 **4201 次**，而原始色值 `#FFFFFF` 只出现 3240 次——**组件几乎不写死色值**，全部走语义变量。这是整套 UI 能长期保持一致的根本原因。

### 2.2 色板：12 色系 × 10 阶（节选 blue / red 实测值）

| 阶     | blue          | L      | S      | red           | L      | S      |
| ----- | ------------- | ------ | ------ | ------------- | ------ | ------ |
| 1     | `#EDF4FF`     | 96     | 100    | `#FEF1F1`     | 97     | 87     |
| 2     | `#D6E6FF`     | 92     | 100    | `#FDDFDF`     | 93     | 88     |
| 3     | `#A6C8FF`     | 83     | 100    | `#FAC1C1`     | 87     | 85     |
| 4     | `#74A9FD`     | 72     | 97     | `#F58F8F`     | 76     | 84     |
| 5     | `#458BFA`     | 63     | 95     | `#F15C5B`     | 65     | 84     |
| **6** | **`#1F69E0`** | **50** | **76** | **`#DD3332`** | **53** | **72** |
| 7     | `#1E5FC7`     | 45     | 74     | `#BB2726`     | 44     | 66     |
| 8     | `#174CA0`     | 36     | 75     | `#9D1C1C`     | 36     | 70     |
| 9     | `#0F3A80`     | 28     | 79     | `#831313`     | 29     | 75     |
| 10    | `#0A306C`     | 23     | 83     | `#6A0B0A`     | 23     | 83     |

**三条硬规律**（蓝色系与红色系同构，证明是同一算法产出）：

- **H 全程恒定**：blue 恒 217°，red 恒 0°。色阶只是明暗变化，绝不让色相漂移。
- **明度递减但不等距**：blue 相邻差 `-4, -9, -11, -9, -13, -5, -9, -8, -5`。两头密（浅色区便于做背景层次）、**5→6 阶差 13（最大跳跃）**，正卡在"主色 ↔ hover"之间，保证状态切换肉眼可辨。
- **饱和度中段下凹**：100% → **76%（第 6 阶=主色）** → 回升 83%。浅色高饱和不会脏（明度够高），深色回升保住色彩感，而中段降饱和正是"不刺眼"的来源。

> **对 EasyShare 的直接意义**：现用 `--blue: #007aff` 的 **S=100%**，正是这套算法要极力避开的区间。

### 2.3 语义层：4 组角色 + 层级化背景

组件只认这四组，不认色相：

| 角色             | 变体                                                            | 实测锚点                                 |
| -------------- | ------------------------------------------------------------- | ------------------------------------ |
| **text**       | primary / secondary / tertiary / public / white / brand       | primary=`gray-10`，secondary=`gray-7` |
| **icon**       | primary / secondary / tertiary / quaternary / white / brand   | primary=`gray-9`（**比文字浅一阶**）         |
| **line**       | 各语义色                                                          | 几乎只用 1px（实测 549 次 vs 0px 206 次）      |
| **fill**       | base / light / regular / medium / heavy / extra-heavy / focus | 7 档灰阶渐变，做控件填充                        |
| **background** | top / middle / bottom / plate / base / frame / group          | 容器分层                                 |

**两个容易被忽略的专业处理**：

- `icon-primary = gray-9` 而 `text-primary = gray-10`——**图标比文字浅一阶**。图形比文字笔画粗，若同色会显得过重。
- `text-success = green-7` 而 `icon-success = green-6`——**文字比图标深一阶**。小字需要更高对比度才看得清。

### 2.4 状态映射：相邻阶，不另造色

```
normal   = X-6      hover = X-5（浅一阶）      pressed = X-7（深一阶）      light = X-1（浅底）
```

实测 `kd-color-brand-normal → brand-6`、`hover → brand-5`、`pressed → brand-7`，五个语义色（brand/public/success/error/warning）全部同构。

### 2.5 尺寸系统（`res/themes/hint.kuip` 全文仅 48 行，是整套几何的唯一来源）

| 类别 | 取值                                              |
| -- | ----------------------------------------------- |
| 圆角 | 2 / 4 / 6 / 8 / 12（`extra-small`→`extra-large`） |
| 字号 | 10 / 12 / 13 / **14** / 16 / 18 / 20 / 24 / 28  |
| 行高 | 18 / 20 / 22 / 24 / 30 / 32 / 36 / 40           |
| 间距 | 4 的倍数：4 / 8 / 12 / 16（`spacing` 出现 88 次为 8）     |

**没有 16px 大圆角、没有 999px 胶囊、没有 15px 字号**。圆角上限 12px（仅弹窗级），日常控件 4~6px。这就是桌面软件的"稳重"——圆角克制。

### 2.6 阴影：越大约淡（反直觉但正确）

| 档            | 颜色                | offset | blur |
| ------------ | ----------------- | ------ | ---- |
| small        | `#0D0D0D` **10%** | y=1    | 4    |
| middle       | `#0D0D0D` **14%** | y=1    | 4    |
| large（浮层/弹窗） | `#0D0D0D` **8%**  | y=12   | 32   |
| extra-large  | `#0D0D0D`         | y=32   | 48   |

大阴影的透明度**反而更低**（8% < 14%）。因为 blur 32 已经把颜色摊开，若仍用 14% 会糊成一团重灰。阴影基色是 `#0D0D0D` 而非纯黑 `#000`。

## 3. 布局范式（像素实测）

### 3.1 WPS：三段式（1920×1031 截图，100% 缩放）

```
┌────┬──────────────┬─────────────────────────────┬────────┐
│ 45 │     259      │          内容区              │  属性   │
│rail│  功能面板     │  面包屑 / 列表                │  详情   │
└────┴──────────────┴─────────────────────────────┴────────┘
```

| 区域       | 实测             | 取值                     |
| -------- | -------------- | ---------------------- |
| 图标 rail  | x 0–44         | **45px**，背景 `#E3E3E3`  |
| 功能面板     | x 55–313       | **259px**，背景 `#F5F5F5` |
| 内容区      | x 315+         | `#FFFFFF`              |
| **列表行高** | y 间距 64–66     | **64px**               |
| 列结构      | 名称 / 最后修改 / 大小 | 名称列占 59%               |

**双栏侧栏（icon rail + 功能面板）是"专业感"的主要来源**——左 rail 放一级品类，面板放当前品类的子导航，比单栏导航更有层次，且不靠文字堆砌。

### 3.2 钉钉：单栏 + 右侧详情（1745×986，约 1.61× 缩放）

| 区域   | 实测     | 折算逻辑值     |
| ---- | ------ | --------- |
| 左侧导航 | 209px  | ≈130px    |
| 内容区  | 1215px | ≈755px    |
| 右侧详情 | 307px  | ≈190px    |
| 列表行高 | 55px   | **≈34px** |

### 3.3 两家的取舍差异

| 维度 | WPS                      | 钉钉                          |
| -- | ------------------------ | --------------------------- |
| 导航 | 双栏（rail+面板），层级清晰         | 单栏，扁平                       |
| 行高 | **64px**，极舒展             | 34px，紧凑密集                   |
| 背景 | 面板 `#F5F5F5` / 内容 `#FFF` | 统一 `#FCFCFC` / 侧栏 `#F8F9FB` |
| 详情 | 右侧常驻属性卡                  | 右侧可关详情面板                    |
| 气质 | 桌面软件，稳重留白                | Web 应用，信息密度高                |

**EasyShare 是 Windows 桌面工具，且文件量不会达到钉钉那种量级 —— 应当走 WPS 的舒展路线。**

## 4. 钉钉的补充观察（像素层）

- 主背景 **`#FCFCFC`**（占 75%），不是纯白 —— 大面积纯白会刺眼，`#FCFCFC` 更耐看。
- 侧栏/顶栏 `#F8F9FB`（H=220 的冷灰），与内容区形成极弱对比（ΔL≈1.5%），靠**大面积色块而非边框**分区。
- 品牌蓝 `#246CF8`（H=220 S=94%），比 WPS 更艳，因为钉钉面向 Web/移动端。
- 选中态是浅蓝底 `#E4ECFC`，**不是实心蓝块**——实心蓝块只用于主按钮。

## 5. EasyShare 现状诊断

### 5.1 token 对照（`frontend/src/style.css:1-21`）

| 项     | EasyShare 现值                                    | WPS 值                     | 差距                     |
| ----- | ----------------------------------------------- | ------------------------- | ---------------------- |
| 品牌蓝   | `#007aff` H=211 **S=100%**                      | `#1F69E0` H=217 **S=76%** | 满饱和，大屏刺眼               |
| 主文字   | `#1d1d1f` H=240 **S=2%**                        | `#262E3E` H=220 **S=24%** | 色相偏紫、饱和度过低→发死          |
| 次文字   | `#6e6e73` H=240 S=2%                            | `#444E63` H=221 S=19%     | 同上                     |
| 弱文字   | `#8e8e93` H=240 S=2%                            | `#8B95A8` H=219 **S=14%** | 同上                     |
| 边框    | `rgba(60,60,67,.12)`                            | `#E4E6EB` 实色              | 半透明叠色不可控               |
| 背景    | `#f0f2f5` + 大渐变 + `backdrop-filter: blur(34px)` | `#FFFFFF` / `#F5F5F5` 纯色  | 渐变+毛玻璃削弱层次             |
| 圆角    | 8px（nav）/ 10px（icon）                            | 4~6px（控件）/ 12px（弹窗）       | 偏大，偏"移动端"              |
| 字号    | 13px 导航 / 11px 辅助                               | 14px 基准 / 12px 辅助         | 基准偏小                   |
| 列表行高  | 37px（`nav-item`）                                | **64px**                  | 密度过高，缺呼吸               |
| 颜色变量数 | 6 个（blue/green/orange/red/purple/border）        | 语义 token 100+             | 无层级、无 hover/pressed 规范 |

### 5.2 五个具体病灶

1. **中性色是纯灰且色相跑偏**：`#1d1d1f` 的 H=240°（偏紫），品牌蓝 H=211°，两者差 29°，视觉上"灰是灰、蓝是蓝"，缺少统一色温。
2. **缺少状态色阶**：hover/pressed 靠 `rgba(118,118,128,.08)` 这类临时半透明叠加，各处不一致，深浅全凭手感。
3. **选中态用渐变实心块**：`linear-gradient(#1688f8,#0878e8)`——iOS 风格。桌面软件的选中应是浅色底 + 左侧色条（或纯色块），渐变在大屏上显得"油"。
4. **毛玻璃叠大渐变**：`radial-gradient` ×2 + `linear-gradient` + `backdrop-filter: blur(34px)`。三层叠加使背景不可预测，且 Windows 上 GPU 合成开销大，滚动时易掉帧。
5. **没有列表行 token**：云盘页的行高、列宽、悬浮态散落在组件里，无法统一。

## 6. 落地建议（按投入产出排序）

### P0：换掉 6 个根变量（改动 20 行，全局生效）

```css
:root {
  /* 品牌：降饱和到 76%，色相统一到 217° */
  --blue: #1F69E0;  --blue-hover: #458BFA;  --blue-active: #1E5FC7;  --blue-light: #EDF4FF;
  /* 中性：注入 220° 蓝相，越浅越去饱和 */
  --text: #262E3E;  --muted: #444E63;  --faint: #8B95A8;
  --border: #E4E6EB;  --border-strong: #D7D9DE;
  --bg: #FFFFFF;  --bg-panel: #F5F7F9;
}
```

> 这一条就能消掉"廉价感"的主体——因为它同时修正了色相、饱和度、层级三件事。

### P1：补状态色阶与尺寸 token

- 每个语义色补 `hover / pressed / light` 三档（用相邻阶，见 §2.4）。
- 圆角收敛到 4/6/8/12，控件一律 6px。
- 字号基准 14px，行高 22；辅助 12px。
- 阴影固定三档（§2.6），大浮层用 `0 12px 32px rgba(13,13,13,.08)`。

### P2：布局改为三段式

`220px 单栏` → `56px rail + 240px 面板 + 内容`，云盘页右侧加常驻属性面板（对标 WPS「研发资料存放」卡：占用空间 / 创建时间 / 更新时间 / 分享 / 回收站）。

### P3：列表行 64px + 三列

名称（含文件类型彩色图标）/ 修改时间 / 大小，行内悬浮才显示 `⋯` 操作菜单。文件类型图标用语义色：文件夹 `blue`、表格 `green`、文档 `navy`、PDF `red`。

### 8.2 两个踩到的坑（下次直接照做）

- **透明叠加必须用深色基**。`rgba(60,60,67,.12)` 是「深灰 + 低 alpha」，等效 `#E8E8E8`；若把基色换成浅灰 `rgba(228,230,235,.12)`，白底上算出来是 `#FCFCFD`，等于没画。正确做法是 `--line-rgb: 38,46,62`（即 `--kd-text-2` 的 rgb），配 `.12` 得 `#E5E6E8`，正对 WPS 的 `line-2 #E4E6EB`。
- **`var()` 不能直接进 `rgba()`**。`rgba(var(--blue), .1)` 无效，必须拆出 `--blue-rgb: 31,105,224` 三元组，再用 `rgba(var(--blue-rgb), .1)`。

## 12. 第五轮：移动文件（前后端打通）

### 12.1 后端

`App.CloudMove(key, targetDir)` → `Client.Move` → 控制面 `/move`。服务端复制对象 + 删源对象，**fileId 不变**，所以分享链接、任务引用、知识索引都不会失效（这正是不能用「下载+上传+删除」替代的原因）。

与 `CloudRename` 的分工：

| 方法                          | 动什么  | 不动什么               |
| --------------------------- | ---- | ------------------ |
| `CloudRename(key, newName)` | 末段名  | 目录位置（显式拒绝 `/`、`\`） |
| `CloudMove(key, targetDir)` | 目录位置 | 文件名（显式拒绝 `..` 逃逸）  |

两者底层同一条 `/move`，拆开只是让调用点能表达「用户到底想干什么」。目标等于源时直接返回，不惊动服务端（避免一次无意义的复制+删源）。

### 12.2 前端

- **目录清单从文件 key 前缀推导**：`/objects` 不返回目录实体，但每条 key 的前几段就是目录，顺路补齐中间层级即可，**不必新增「列目录」接口**。
- **平铺 + 缩进**而非可折叠树：目录树要展开两次才能点到深层目录，平铺一次点击就到位，目录多时靠滚动。
- 选中源文件所在目录时提交按钮变「已在目标目录」并禁用——不允许触发一次空移动。
- 移动成功后清空选中、刷新列表（文件已不在当前目录）。

### 12.3 顺手修正的一个错误

详情面板的「位置」原本用**当前面包屑**。但搜索结果里的文件可能在子目录，此时面包屑指的是「你在哪」而不是「文件在哪」，位置会指错；移动时判断「是否原地不动」也会跟着错。

改为从 `file.key` 推导（`detailDir`），面包屑只负责表达当前位置。

### 12.4 为什么没做文件夹的移动/重命名

`DriveMoveService.move` 是**单路径**操作：

```java
fileService.moveRegistered(spaceType, ownerId, from, to);
storage.copyAt(prefix, from, to);
storage.deleteAt(prefix, from);
```

目录要递归遍历所有子对象逐个搬，且中途失败需要整体回滚——那套补偿逻辑（先占名字、失败挪回、清理副本）在单文件上已经写了 40 行注释，扩展到子树的事务边界风险远高于本轮范围。要做应当单独立项。

## 13. 第六轮：批量选择与批量操作

### 13.1 为什么只对文件开放

目录的移动/删除在后端仍是**单路径**操作（§12.4）。在递归事务边界没解决之前给出「批量选文件夹」的入口，等于把「看起来能用、实际会留半截状态」的功能交给用户。所以：

- 勾选框只出现在**文件行**；
- 列头的全选只覆盖当前目录的文件；
- 文件夹行保持「点一下进入」的单一语义。

### 13.2 交互设计

| 决策    | 做法                         | 理由                                    |
| ----- | -------------------------- | ------------------------------------- |
| 勾选框放哪 | **复用文件图标的位置**：悬停时图标淡出、方框淡入 | 不额外占一列宽度，三列的对齐不会被破坏                   |
| 勾选后   | 方框常驻（不随 hover 消失）          | 用户需要随时看到「哪些已经选了」                      |
| 批量操作条 | 有选中项时**顶掉**常规工具条           | 两套操作同时占着顶部，用户会分不清当前是哪种模式              |
| 换目录   | 立即作废勾选                     | 否则「已选 3 项」里混着看不见的文件，批量操作会作用到用户看不到的对象上 |

### 13.3 部分失败的如实反馈

控制面没有批量接口，删除/移动都是**逐条循环**。单个失败不中断整批，但结果必须让用户看见——否则「点了删除、列表里还剩两个」会被当成 bug。

- 批量删除：`已选 N 项 → 逐条删 → done < keys.length 时顶部红条提示「X 个文件删除失败」`；
- 批量移动：同样收场（成功的已经搬走），失败数用同一条顶部提示告知，而不是把弹窗留着让用户以为整批没动。

### 13.4 一并清掉的死代码

移动改成逐条 try/catch 之后，`moveError` 再没有赋值点（失败统一走顶部提示），连同模板里的 `<p v-if="moveError">` 和对应 CSS 一并删除。

## 14. 第七轮：桌面手感（右键菜单 / 键盘 / 双击）

### 14.1 右键菜单

| 决策     | 做法                                                                 | 理由                                         |

## 15. 回收站保留期（把「30 天」变成事实）

### 15.1 先纠正一个事实

原来的删除确认框写的是「删除后将无法从云端恢复」，而实际是软删、回收站可还原——**文案与行为相反**。

更关键的是：**「保留 30 天」此前根本没有实现**。`es_file` 里的 `recycled` 行无限期保留，对象也不清理，回收站只增不减。

所以这一轮不是改个文案，是把这条规则做出来，否则「保留 30 天」就成了第二句谎话。

### 15.2 后端

| 文件 | 作用 |
| --- | --- |
| `DriveSchedulingConfig` | `@EnableScheduling`。单独立类而不是挂启动类：platform-drive 是可选模块，调度开关跟着模块走，不依赖 ruoyi-admin |
| `RecycleJanitor` | 每天 03:30 扫 `state='recycled' AND deleted_at < now - 30d`，逐条 `purgeFromRecycle`（对象 + 行一起清） |

**失败策略**：单条失败只记日志、继续下一条。下次调度会重新扫到它——清理是幂等的，`purgeFromRecycle` 对已被清掉的行会抛错，那只会让它退出待清理集合，不会留下半截状态。

避开业务高峰选凌晨；`purgeExpired(LocalDateTime now)` 显式接收「以哪个时刻为现在」，便于测试边界而不必真等 30 天。

### 15.3 常量的单一事实来源

| 位置 | 值 | 用途 |
| --- | --- | --- |
| `RecycleJanitor.RETENTION_DAYS` | 30 | 真正执行清理的天数 |
| `types/core.ts` → `RECYCLE_RETENTION_DAYS` | 30 | 删除确认、回收站空状态文案 |

两处各自注释里都写明「改一处必须改另一处」。**不把天数硬编码进文案**，否则改保留期时一定会漏掉某句提示。

### 15.4 改后的文案

- 删除确认：`确定删除「xxx」？删除后可在回收站还原，回收站保留 30 天。`
- 回收站空状态：`删除的文件会保留 30 天，期间可随时还原。`

### 15.5 验证与已知边界

Java `mvn compile` ✅｜前端 `npm run build` ✅｜`npm test` 45 tests ✅

- 清理任务**没有单测**：需要 mock MyBatis-Plus 的 `selectList`，而逻辑本身是「查一批 + 循环调用已有方法」，编译期就能挡住大部分错误，剩下靠人工审阅。
- **多实例部署会重复调度**：各节点同时扫到同一批行，`purgeFromRecycle` 抛错后记日志——幂等所以不会损坏数据，只是日志噪音。真要多节点再考虑分布式锁。

## 16. 回收站功能的收尾（测试 / 倒计时 / 布局修正）

> 多实例部署已确认不会出现，本节不涉及分布式锁。

### 16.1 清理任务的单元测试

`RecycleJanitorTest`，3 个用例：

| 用例 | 断言 |
| --- | --- |
| 拿到几条就清几条 | 返回 2 行 → `purgeFromRecycle` 调 2 次、返回 2 |
| 单条失败不中断整批 | 中间那条抛异常 → 三条都被调用、返回 2（失败的不计入） |
| 没有过期记录时不打搅下游 | 空列表 → `never()` |

**测什么、不测什么**：`state='recycled'` 与 `deleted_at < cutoff` 由 `LambdaQueryWrapper` 表达，在真实 DB 里生效；纯 mock 环境里 `selectList` 直接返回预置列表，过滤条件不会被执行。所以测试只覆盖**拿到一批行之后的行为**，过滤条件靠代码审阅。

静态初始化与 `DriveFileServiceTest` 相同：手工调用 `TableInfoHelper.initTableInfo`，否则 `EsFile::getState` 的 lambda 解析会抛 `can not find lambda cache for this entity`。

### 16.2 回收站显示倒计时

「保留 30 天」如果只是文案，用户仍然不知道**自己还剩多久能反悔**。列表副标题改为：

```
originPath · 2.4 MB · 删除于 10/17 10:12 · 还剩 29 天
```

- 天数从 `deletedAt` 现算，不落库——保留期调整后旧数据自动按新规则显示；
- 最后 3 天文案换成「仅剩 N 天」，这时候紧迫性本身就是信息；
- `deletedAt` 缺失（老数据）时**不显示倒计时**，而不是编一个天数。

拼装集中在 `rowMeta()` 一个函数里，模板只负责展示——避免同一个计算在标签内被调用三次。

### 16.3 连带修掉的布局缺陷

第 11 轮把 `.cloud-row` 从 flex 改成 4 列 grid（图标 / 名称 / 修改时间 / 大小），但**回收站面板复用了同一个类**，而它只有「图标 / 信息 / 操作」三个元素——信息列被压在 `1fr` 里，右侧白白空出两列的位置。

修法：`.recycle-panel .cloud-info { grid-column: 2 / -1; }`，让信息区跨满剩余宽度。操作按钮本就是绝对定位浮在行尾，不受影响。

> 教训：把一个通用类改造成 grid 之前，先 grep 有多少个地方在复用它。这次是靠肉眼发现的，不是编译期发现的。

## 17. 文件分享：从 10 分钟预签名到可撤销外链

### 17.1 先纠正一处文案

`CloudShare` 的代码注释写着「预签名 URL，默认 10 分钟，**不接受调用方指定小时数**」，而前端 `requestShare(key, 24)` 与界面文案都是「24h 有效」。这是本轮发现的第三处**文案与行为相反**。

预签名地址的致命缺陷不是短，而是**不可撤销**——发错了只能等它过期。企业场景里「想收回」是高频需求，这才是分享层存在的理由。

### 17.2 公开端点为什么走 Filter

`GET /easyshare/s/{token}` 必须免登录。项目里做不到「加个注解」：

| 方案 | 为什么不行 |
| --- | --- |
| `@SaIgnore` | 鉴权是 `SaRouter.match(allUrlHandler.getUrls())` 全量拦截，注解模式不生效 |
| `security.excludes` | 配置在 **gitignore 的 `platform/`（RuoYi 工程）里**，改了不进仓库，部署必漏 |
| **Servlet Filter** ✅ | 天然早于 MVC 拦截器；自包含、不依赖部署配置、40 行可审计 |

安全取舍：不存在 / 已撤销 / 已过期**统一 404**，不区分原因——否则这条链接会变成探测 token 是否有效的工具。

### 17.3 分享记录的设计

- token：base62 22 位 ≈ 128 bit 熵，不依赖自增、不可枚举
- `file_name` / `file_size` 是**创建时快照**：文件后来被删，列表仍要能说明这行是什么
- 失效有两个来源（`expires_at`、`revoked`），撤销立即生效、不等过期
- 默认 7 天、上限 30 天，规则只在控制面一处（客户端不二次裁剪）

## 18. 版本历史：留档必须抢在 presign-put

### 18.1 时序决定一切

客户端直传对象存储，覆盖发生在「拿 URL」与「登记」两次 API 之间：

```
presign-put ──→ 客户端 PUT（旧对象在此被覆盖）──→ register
     ↑                                                    ↑
  只有这一刻能抢救                                    已经晚了
```

所以 `snapshot` 挂在 presign-put：查当前 active 行 → `copyObject` 到 `.versions/{path}/v{n}` → 写历史行。服务端复制，不耗客户端带宽。

**代价**：客户端拿了 URL 却没真上传时，会多一份无用副本。「浪费一点存储」对「永久丢失用户内容」，选前者。

### 18.2 回滚本身也要可撤销

`restore` 的第一件事是**给当前内容留档**，然后才把旧版本复制回主路径。否则「恢复到 v2」会把你现在这一版永久丢掉——回滚就成了不可撤销的破坏。

回滚后版本号**继续 +1，不退回旧号**：`version_id` 单调是乐观并发校验的前提，退号会让所有客户端手里的 `expectedVersion` 瞬间失效。

### 18.3 实现细节

- 版本对象存 `{prefix}.versions/{path}/v{n}`，与正常文件隔离
- `/objects` 与 `/changes` 两处 `listAt` 都过滤 `.versions/`——快照是实现细节，不是用户文件
- `(file_id, version_id)` 唯一索引：presign 重试不产生重复历史（并发时第二笔插入被挡住，静默即可）
