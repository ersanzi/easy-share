# EasyShare 版本迭代指南

本文定义后续版本的固定开发流程（**纯流程文档，不记录事实状态**）。开始迭代时，将"版本工作区模板"复制到 `iterations/YYYY-MM-DD-<版本或主题>.md`，并随代码维护；结束后保留决策和验收结果，避免下次重新考古。

## 1. 迭代前先对齐事实与方向

- **当前可依赖的行为**以 [`architecture.md`](architecture.md) 为准——它描述进程、端口、API 和生命周期的当前事实，任何迭代都不应无意破坏其中列出的行为。
- **下一步做什么**以 [`progress.md`](progress.md) 的「路线总览」和「待开始（按优先级）」为准，本文不维护候选方向清单。
- 涉及长期架构取舍时，先查 [`adr/`](adr/README.md) 中对应决策的状态与开放问题。

## 2. 版本工作区模板

开始下一版时复制为 `docs/iterations/YYYY-MM-DD-<版本或主题>.md`。目录规则见 [`iterations/README.md`](iterations/README.md)。

```markdown
# EasyShare <版本/主题>

## 用户问题
- 当前谁在什么场景下遇到什么问题？

## 目标
- 可观察、可验收的结果 1
- 可观察、可验收的结果 2

## 非目标
- 本次明确不做什么

## 设计决策
- 数据/协议/UI/生命周期如何变化
- 为什么选择该方案
- 放弃了哪些替代方案

## 兼容与迁移
- config.json 是否新增字段
- 旧 Core/新 UI 是否可能共存
- 是否涉及残留盘符、端口、文件或凭据

## 测试计划
- 单元测试
- 前端测试
- Windows 集成测试
- 双机局域网验收

## 发布与回滚
- 构建产物
- 升级步骤
- 回滚方式
- 日志和监控信号

## 完成记录
- 已完成项
- 已知问题
- 测试结果与日期
```

## 3. 每次迭代的执行顺序

### A. 开始前

1. 阅读 `architecture.md` 和相关历史实现。
2. 从日志或用户场景写清问题，不要先假设技术方案。
3. 填写目标、非目标和验收标准。
4. 标记兼容风险：配置、端口、API、盘符、进程和自动生成绑定。
5. 为高风险流程先写失败场景测试。

### B. 实现中

1. 小步改动，保持桌面/Core 两个进程的协议兼容。
2. API 签名变化时同时更新 Client、Wails bridge、前端 service 和文档。
3. 配置变化必须提供旧配置迁移，不能只修改默认结构体。
4. 生命周期变化必须覆盖启动、窗口关闭、全退出、崩溃和重复启动。
5. 日志应包含操作、目标和系统错误，但不得记录 Token 或密码。

### C. 交付前

1. `go test ./...`
2. `npm --prefix frontend test`
3. `npm --prefix frontend run build`
4. `scripts/build.ps1`
5. 手工验收：Windows 按 [`testing/knowledge-service-checklist.md`](testing/knowledge-service-checklist.md)（知识服务）及迭代记录中的验收清单执行
6. 涉及发现/传输时做两台机器验收
7. 检查没有残留盘符和 EasyShare 进程
8. 更新 README、架构、排障和本迭代完成记录

## 4. Definition of Done

一个版本只有在以下条件全部满足时才算完成：

- 用户目标和非目标清晰，范围没有暗中扩大。
- 新行为有自动化测试，高风险 Windows 行为有真实集成验证。
  - **冲刺期豁免（2026-08-21 用户指示）**：发芽路线冲刺切片默认不写新单测，交付门槛降为「既有回归全绿 + 构建通过 + 手工冒烟」；转入企业级改造（Java 控制面迁移等）时恢复全项，迁移类改造动手前先补协议一致性测试。
- 完整生产构建成功且两个 EXE 同时交付。
- 退出后无残留 EasyShare 映射或进程。
- 日志足以定位失败，并且不泄露密钥。
- 当前文档与代码一致，历史文档被明确标记为历史。
- 已知限制、升级方式和回滚方式已记录。
