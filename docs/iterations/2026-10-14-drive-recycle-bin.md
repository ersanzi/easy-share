## 范围

做：
1. es_file 加列：`state`（active/recycled/purged）、`deleted_at`、`origin_path`、`origin_parent_id`、`version_id`；DDL 幂等（`deploy/ruoyi-db/easyshare-file-recycle.sql`）
2. `uk_es_file_path` 唯一索引改为部分索引（`WHERE state='active'`），回收站内同路径不冲突
3. 删除改软删（保留 RustFS 对象）；列表只出 active
4. 回收站 API：列表 / 还原（origin_path 复位，原路径被占则报可读冲突）/ 彻底删除（连对象一起删）
5. 版本号：同名覆盖上传时 `version_id` 单调递增（历史列表/回滚不做，留字段）
6. Go Core 封装 + 版本化路由；前端网盘页「回收站」视图（列表/还原/彻底删除，破坏性操作有确认）

不做：重命名/移动、错误三件套、多选批量、版本历史 UI、星标/标签（P2 排期见对标文档 §6）

## 验收门槛（对标 §9）

1. 挂 fileId，不新增路径绑定
2. 删除可还原、还原到原位置
3. 破坏性操作前有确认，失败原因对人可读
4. 不新增普通用户需要理解的技术设置
5. 与阶段 5 共用同一文件模型，不产生第二套真相源

### 收尾期间修复的七个高危缺陷

本轮验收时发现并修复（详见 [`known-issues.md`](../known-issues.md)）：

- **KI-10（回收站整条链路失效）**：软删只改目录行、不动 RustFS 对象，
  而列表出口**没按 state 过滤**——存储列举里照样有这条对象，惰性补账于是
  insert 一条新 active 行，等于**列表自己把删除撤销**。三重后果：
  ①文件照旧出现在列表里（像「删不掉」）；②还原永远报「原位置已有同名文件」，
  而占位者正是列表自己插的那行，用户看不见也删不掉；
  ③彻底删除时引用计数（KI-7）认为还有债主，**对象永不释放**。
  修复：列表三步（查库 → 藏软删 → 回填 fileId）**收成唯一公开入口**
  `DriveFileService.list(...)`，两个内部步骤降为 `private`——
  这三步的配套关系是正确性的一部分，拆开暴露就等于允许「漏一步」而不报错。
  状态判定走**白名单**（只有 `active` / `state IS NULL` 算在用），
  将来新增状态默认落安全侧。
  这是**读侧漏了跟随写侧**——与本仓 KI-9（`Seek` 漏 `(0, SeekStart)`）同一类错误。
- **KI-7（数据丢失）**：彻底删除回收站旧行会误删同路径的**当前**文件。
  根因是对象键由路径派生 + 软删保留对象 + purge 不检查占用。
  修复后按**引用计数**语义：还有别的行指向该路径就不删对象，最后一个引用消失才删。
  （**第一版修复只查 active，是错的**——见 KI-7 的「判据修正」小节。）
- **KI-8（验收无效）**：`platform-drive` 的 Java 测试**从未真正运行**——
  父 POM 的 `maven.test.skip=true` 让 `mvn test` 报 `BUILD SUCCESS` 却一个测试都不跑。
  这意味着**本迭代此前的任何「测试通过」结论都不成立**。
  修复后测试默认真跑：`mvn -o clean test` → **57 passed**（KI-10/11/12 全部修复后为 **71**；KI-13 是 Go 侧，见下表）。
- **KI-11（权限绕过）**：文档级可见性只在**列表出口**过滤，`/presign-get` 既不查可见性
  也不查 state——知道路径的人能直接签出下载 URL 拿走受限文件，软删的文件同样照签。
  「看不见」被当成了「拿不到」。修复把可见性判据抽成 `sharedRowVisible`
  （列表过滤与下载校验**共用同一份实现**），并在下载口加 `assertDownloadable`。
  与 KI-10 同属「校验只放在某一条路径上，没放在所有必经之路」这一形状。
- **KI-12（空间泄漏 + 引用失效）**：`spacedav.Rename` 一直是「下载 + 上传 + 删除」
  的模拟改名，而本片的软删改造把控制面删除从物理删换成软删——于是每次改名
  **都留一份完整副本进回收站（空间 ×2）**，且上传新键会**换掉 fileId**
  （分享链接/任务引用/知识索引全断）。修复：新增 `POST /drive/move`
  （`CopyObject` 服务端复制 + 改行 + 删源，字节不出对象存储、fileId 不变），
  编排收在可单测的 `DriveMoveService` 并带失败补偿。
  这是**路线图切片 4 第 2 项落地**，也是本片引入的回归。
- **KI-13（OOM）**：`internal/spacedav` 的 WebDAV 写路径用 `bytes.Buffer` 攒整份内容，
  拖一个 5 GB 文件就是 5 GB 分配。原注释说「真正的解法需要控制面先支持 multipart」——
  **那条前提早在 2026-09-06 就成立**（上传会话四端点 + 客户端 32 MiB 分流），
  只是代码没跟上。修复改**落盘暂存**，并把本地路径交给分片通道，
  顺带让资源管理器拖入的大文件也能分片 + 断点续传。


- **KI-14（数据丢失）**：切片 5 叫「只读占位符」，但那个「只读」**没有执行层依托**——
  cfapi 只注册读回调（`FETCH_DATA`/`CANCEL_FETCH_DATA`），占位符又是
  `FILE_ATTRIBUTE_NORMAL`。实测三段：编辑保存**成功** → 改动**不上传** →
  重建一旦能正常跑（带 `SUPERSEDE`）就**被覆盖成 0 字节**。
  修复：打 `FILE_ATTRIBUTE_READONLY`，实测写入被拒且**水合不受影响**。
  **这是接入 `app.go` 前自查拦下的**——直接挂上去，用户第一天就会撞上。
  顺带发现 `Sync` 声称「可重复调用」实测不成立（`ERROR_ALREADY_EXISTS`），
  **刻意暂不修**：当前还没丢数据只是因为重建本身是坏的，
  谁去修那个更显眼的 bug，谁就同时打开数据丢失那条路。

### 真实端到端联调（2026-10-16 完成，**验收口径达成**）

上面的「真实数据库联调」只覆盖到**数据库层**。本轮把**整条链路**跑通了：
`docker compose up -d`（PG 16 + Redis 7）+ `deploy/ruoyi-db/run-ruoyi-admin.ps1`
（控制面 8090）+ 已运行的 RustFS（9000）——**三件套齐活**，
于是可以真正验证「客户端 → 控制面 → 对象存储」的全链路。

**实测流程（每一步都是真实 HTTP + 真实数据库 + 真实对象存储）**

| # | 动作 | 结果 |
| --- | --- | --- |
| ① | `POST /auth/login` | 200，拿到 504 字符 token |
| ② | `POST /space/admin/personal-quota` 分配 1 GiB | 200 |
| ③ | `POST /drive/presign-put` 取上传 URL | 200 |
| ④ | `PUT` 直传 RustFS | 200 |
| ⑤ | `GET /drive/objects` | 看到 `fileId=2110926611355803650`（**真实雪花 ID**） |
| ⑥ | `DELETE /drive/object`（按 fileId 软删） | 200 |
| ⑦ | 再列举 | **条目数 0** —— KI-10 的核心断言成立 |
| ⑧ | `GET /drive/recycle` | 1 条，`originPath=e2e/probe.txt` 快照正确 |
| ⑨ | `POST /drive/recycle/restore` | 200，列表重新出现且 **fileId 不变**，回收站清空 |
| ⑩ | 删掉 → 重新上传同名 → purge 旧行 | 新文件拿到**不同** fileId |
| ⑪ | **purge 后读新文件内容** | `NEW-FILE-CONTENT` —— **KI-7 的数据丢失场景不复现** |

**第 ⑦ 与第 ⑪ 条是本迭代最有价值的两条证据**：

- **⑦** 验证 KI-10（回收站读侧失效）：修复前，删掉的文件会**立刻回到列表里**，
  而且还原永远报「原位置已有同名文件」（占位者正是列表自己插的行）。
  现在删掉就是删掉。
- **⑪** 验证 KI-7（数据丢失）：这是「对象键由路径派生 + 软删保留对象」
  这条设计的**唯一危险点**——删旧行时若按路径删对象，
  会把用户**重新上传的同名文件**一起删掉。实测新文件内容完好。

**逐项实测结果（全部在真实 PostgreSQL 上执行，非模拟）**

| 检验项 | 方法 | 结果 |
| --- | --- | --- |
| **迁移路径**（旧 schema → 新 schema） | 先只建旧版 `es_file`（全量唯一索引），再跑 recycle DDL | ✅ 五个列全部加上；`uk_es_file_path` 从**全量唯一**变**部分唯一**（`WHERE state='active'`） |
