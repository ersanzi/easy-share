# 2026-08-29 悬浮窗布局重构与固定态（切片 2）

> 前置切片：[2026-08-28 托盘悬停浮窗（切片 1：悬停链路）](2026-08-28-tray-hover-widget.md)

## 用户问题

切片 1 交付的浮窗只有一条 320×56 的标题栏。用户实机验收后反馈：宽度可以接受，**高度明显不够**，
无法承载后续要加的能力（固定、拖入文件、自动整理），要求先把尺寸与分区调整好，
让后续功能有地方落。

同时用户希望的「桌面右下角常驻悬浮窗」在实机上没有出现——因为切片 1 根本没做这个形态，
当前只有通知区域图标的悬停面板（该形态已实机验证可用）。

## 关键分析：为什么固定态必须先做

**悬停态无法承载文件拖放。** 这不是实现难度问题，是交互上的死结：

```text
用户想拖文件进浮窗
  → 必须先按住文件开始拖动
  → 此时鼠标已经离开通知区域图标
  → 悬停条件不成立，浮窗收起
  → 没有可放置的目标
```

所以「拖文件进去」的前提是浮窗**能脱离悬停条件继续存在**，也就是固定态。

由此得到一个统一模型——用户要的两种形态不是两个部件，而是**同一个窗口的两种状态**：

| 状态 | 触发 | 生命周期 | 能否拖放 | 对应用户描述 |
| --- | --- | --- | --- | --- |
| 悬停态 | 悬停通知区域图标 | 移开即收起 | 否 | 「悬浮到图标就弹窗」 |
| 固定态 | 在悬停态点「固定」 | 常驻，直到取消固定 | **是** | 「桌面右下角常驻的小窗」 |

这比实现两个独立部件更省事，也避免了两套状态、两套定位、两套拖放逻辑。切片 1 的窗口、
WebView2 嵌入、定位计算与标题栏页面全部可直接复用。

## 目标与非目标

### 目标

1. 浮窗按内容分区重构，高度扩大到能承载拖放区与结果列表。
2. 标题栏增加「固定」按钮，点击后浮窗进入固定态：不再随鼠标移开收起。
3. 固定态支持拖动窗口改变位置，位置持久化到配置，下次启动沿用。
4. 固定态下取消固定则回到悬停态并收起。
5. 尺寸与分区高度集中为命名常量，便于后续调整，不散落在 CSS 与 Go 两处。
6. 悬停态与固定态共用同一套 HTML，通过状态类切换外观，不做两个页面。

### 非目标

- **不做**文件拖入的实际接收与上传（切片 3）。本切片只把拖放区**画出来**并占好位置，
  区域内显示「固定后可拖入文件」提示。
- **不做**自动整理算法（切片 4）。
- **不做**最近文件的真实数据（切片 3 起接入）。本切片列表区显示空状态占位。
- **不做**收起成小图标停靠屏幕边缘的第三种形态。先验证固定态是否够用。
- **不改** macOS。
- **不改**主窗口。

### 验收标准

1. 悬停图标 → 浮窗以新尺寸弹出，各分区布局正常，无内容溢出或裁切。
2. 点「固定」→ 鼠标移开浮窗不再收起；按钮呈激活态。
3. 固定态下按住标题栏空白处可拖动窗口；松手后位置保留。
4. 重启 EasyShare → 固定态与窗口位置恢复。
5. 固定态下再点「固定」→ 取消固定，浮窗收起，恢复悬停行为。
6. 固定态下点设置图标 → 主窗口显示，浮窗保持固定不消失。
7. 拖动到屏幕边缘时窗口仍完整可见，不跑出工作区。
8. 150% 缩放下各分区比例正常。
9. 退出 EasyShare → 固定的浮窗一并消失，无残留窗口。
10. `go test ./...`（除既有 KI-4）、前端测试、`wails build` 通过。

## 尺寸与分区设计

用户明确「宽可以了」，因此宽度保持 **320**（逻辑像素，按 DPI 缩放）。高度按内容需要重算。

```text
悬停态  320 × 220                       固定态  320 × 420
┌──────────────────────────┐          ┌──────────────────────────┐
│ [图] 私人云盘  [我][📌][⚙] │ 56       │ [图] 私人云盘  [我][📌][⚙] │ 56
├──────────────────────────┤          ├──────────────────────────┤
│ ● 连接正常                │          │  ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐  │
│   设备 2   任务 0         │ 76       │  │   拖文件到此处      │  │ 132
├──────────────────────────┤          │  └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘  │
│  固定后可拖入文件         │ 88       ├──────────────────────────┤
│  [固定]                   │          │ 最近整理                  │
└──────────────────────────┘          │   （空状态占位）          │ 200
                                       ├──────────────────────────┤
                                       │ 已连接 · 0 个任务         │ 32
                                       └──────────────────────────┘
```

高度取值依据：

| 分区 | 高度 | 依据 |
| --- | --- | --- |
| 标题栏 | 56 | 切片 1 已验证；容纳 26px 图标 + 28px 按钮加上下留白 |
| 拖放区 | 132 | 拖放目标需要足够大才好命中；虚线框内含图标 32 + 文字 20 + 上下留白 |
| 列表区 | 200 | 分区标题 28 + 4 行 × 40（24px 文件图标 + 上下 8 留白） |
| 状态条 | 32 | 单行 12px 文字加上下留白 |
| 悬停态摘要 | 76 | 两行：状态点 + 三项计数 |
| 悬停态提示 | 88 | 一行提示 + 一个固定按钮 |

宽度校验：320 减去左右各 10 padding 得 300 可用宽度。列表行内「文件名 + 时间」按
文件名 210 + 时间 80 分配，中文文件名约可完整显示 13 字，超出省略。若实测截断过多，
再考虑放宽到 360——但需用户确认，因为用户已表态宽度可接受。

## 技术决策

### 1. 尺寸常量集中在 Go 侧，CSS 用 CSS 变量接收

切片 1 把 `hoverPopupWidth/Height` 放在 `tray_hover_asset_windows.go`，而分区高度若写死在
CSS 里，调尺寸就要改两处且容易不同步。改为：Go 侧定义各分区高度常量，注入为 CSS 自定义属性
（通过 `chromium.Init` 注入或在 HTML 里用占位符替换），CSS 只引用变量。

窗口总高由 Go 按状态计算，避免「窗口高 420 但内容只有 300」这类不一致。

### 2. 固定态改变的是收起策略，不是窗口实现

固定态不新建窗口，只在 `hoverPopup` 上增加 `pinned bool`：

- `pinned == true` 时，`scheduleHideOnOwnThread` 直接返回，短路整个收起路径；
- 托盘的 `NIN_POPUPCLOSE` 分支同样在固定时不触发收起；
- 窗口尺寸按状态调用 `MoveWindowTopMost` 重设。

这样固定态不引入新的生命周期，退出路径与切片 1 完全一致。

### 3. 窗口拖动用 `WM_NCHITTEST` 返回 `HTCAPTION`，不自己算增量

标题栏空白区拖动窗口的标准做法是让该区域在命中测试时被当作标题栏，由系统接管拖动，
比在 JS 里监听 mousemove 再 `SetWindowPos` 更顺滑，也自动获得吸附与多屏处理。

但浮窗内容由 WebView2 渲染，鼠标消息先进 WebView2。做法：页面在标题栏空白处监听
`mousedown` 后 postMessage 通知 Go，Go 侧调用 `ReleaseCapture` + `SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)`
把拖动交还系统。这是 Electron/CEF 无边框窗口的通用手法。

### 4. 位置与固定状态持久化进现有 config.json

新增字段而非另建文件，复用 `internal/config` 已有的原子写入与热加载：

```text
widget.pinned      bool
widget.x, widget.y int    固定态窗口左上角（屏幕坐标）
```

按 `internal/config` 既有约定提供默认值与校验：坐标需落在某个显示器的工作区内，
否则回落到「通知区域图标附近」的默认定位——显示器拔掉后不能让浮窗跑到看不见的地方。

**注意**：新增配置字段会触及 Wails 绑定级联（`AGENTS.md` 第 11 条），
若字段暴露给前端需同步 `frontend/src/types/core.ts` 与 `services/core.ts`。
本切片的 widget 配置只在桌面端内部使用，不暴露给 Vue 主界面，因此不触发级联；
一旦后续要在设置页里配置它，必须走完整级联。

### 5. 拖放区在本切片只是占位，但 DOM 结构按最终形态写

区域用 `dragover/drop` 的 DOM 结构与 class 提前写好，事件处理留空并显示提示文字。
这样切片 3 接真实拖放时只填事件，不动布局，避免二次重排。

WebView2 接收系统文件拖放需要额外配置（默认不透传 `CF_HDROP`），这一点在切片 3 处理，
本切片先记录为已知风险。

### 实际交付的行为

```text
双击 exe      → 只常驻托盘图标，不自动弹浮窗（像腾讯/WPS）
悬停托盘图标  → 弹出浮窗（悬停态，184 高）
点 📌 固定    → 浮窗加高到 360、常驻、出现拖放区占位；再点取消固定
点 ⚙ 设置     → 显示主窗口（固定态下不收起浮窗）
移开鼠标      → 未固定即收起；固定则保留
```

### 相对原计划的偏差

1. **取消了「启动即固定」（原计划的 B 形态）**。实现过一版「双击 exe 自动在右下角弹固定浮窗」，
   用户实测后认为启动就弹窗突兀，且期望的是托盘图标常驻。改为 `startPinned=false`：
   启动只挂托盘图标，浮窗按悬停/固定的交互出现。代码保留了 `startPinned` 参数与 `enterStartPinned`
   路径，未来若要恢复自动固定，`newHoverPopup(..., true, ...)` 即可。
2. **窗口拖动、位置持久化未做**。用户当前不需要移动窗口（固定后停在右下角即可），推迟到需要时再加。
3. **新增：托盘图标稳定 GUID + 持久化**（原计划未覆盖，实施中因用户「图标不在通知区」的诉求引入）。

### 关键技术决策（新增）

- **托盘图标用稳定 GUID（`NIF_GUID`）**：Windows 11 把新托盘图标默认丢进 `^` 溢出区，
  应用**无法用代码强制**进入常显区（系统限制，直接写注册表 `IsPromoted=1` 实测也不生效）。
  带稳定 GUID 后，用户手动提升一次（拖出 `^` 或设置里开），系统按 GUID 记住偏好，
  跨重建/重启持久。GUID 固定为 `{E45A9B3C-7D21-4F6E-A8B2-3C9D1E5F7A80}`，**切勿更换**
  （换了等于新图标，用户既有摆放丢失）。
- **处理 `TaskbarCreated` 广播**：explorer 重启时会广播该消息，应用须借此重新 `NIM_ADD` 图标，
  否则 explorer 崩溃/重启后图标永久消失。经 `winui.RegisterWindowMessage("TaskbarCreated")`
  注册，在 `trayWndProc` 中重挂。

### 踩的坑（排障补充）

1. **`NavigationCompletedCallback` 不可靠**：原打算用它在页面就绪后 `Eval(applyPinned)`，实测回调未触发。
   改用 `chromium.Init()` 在页面脚本运行前注入 `window.__esStartPinned` 标志，页面 onload 自行套用样式。
2. **启动即显示导致浮窗透明**：在消息循环 `RunMessageLoop` 运行**之前**显示窗口，WebView2 不渲染，
   窗口 `visible=True` 却完全透明（穿透到桌面）。改为投递 `hoverMsgStartPinned`，由循环运行后再显示。
3. **`Shell_NotifyIconGetRect` 须按 GUID 查**：图标以 `NIF_GUID` 注册后，定位查询也要传 GUID，
   否则悬停浮窗定位失败。
4. **多次构建产生多条注册表残留**：老 systray 版（UID=100）、首版原生（UID=1）、GUID 版各留一条
   `NotifyIconSettings` 条目，导致设置界面出现多个「EasyShare」、用户点错。清理为仅保留 GUID 条目。
5. **取消固定后浮窗消失**：取消固定时把窗口缩回悬停高度并重定位（底部锚定 → 变矮时顶边下移），
   而鼠标此刻停在固定按钮（顶部），窗口一挪就跑到光标下方，随后「光标不在窗内」判定成立 → 立即隐藏。
   修复：取消固定时**不缩放、不重定位、不强制隐藏**，只切回悬停样式并标记指针在窗内，
   由真实 mouseleave 触发常规延迟收起；下次悬停以悬停高度正常弹出。
