# 2026-10-18 · 非空文件夹递归删除（切片 4 补齐）

## 背景

上一轮补上「新建文件夹」后复查对标吸收情况，发现一处**同一个动作在两个入口语义不同**：

- 挂载盘（资源管理器）删非空文件夹：`internal/spacedav` 早已自己列举子树、逐个删对象，能删。
- 网盘页删非空文件夹：前端直接拒绝——`「xxx」不为空，请先删除或移出其中的文件`。

依据是钉盘取证 §9「服务端改名/移动」与「目录对象」两行，以及 WPS 取证 §10 的 `to_delete_files`
待删队列：**删除一个目录就是删除它整棵子树**，没有「先清空再删」这种用户负担。

## 改动

| 层 | 位置 | 做了什么 |
| --- | --- | --- |
| 控制面接口 | `platform-drive/.../DriveController.java:342` | `DELETE /object` 新增 `recursive`（`PathBo` 加一个 `Boolean`，缺省即旧行为）；目录键带尾斜杠且 `recursive=true` 才走子树分支，带 `fileId` 时不走（身份删文件的语义不被污染） |
| 目录层服务 | `DriveFileService.java:425` | `recycleSubtree`：按前缀捞出子树内在用行，逐个软删进回收站。扫描条件带 `state IS NULL`——读侧把存量 NULL 行当在用，漏了就会出现「文件夹删了、里面文件还在」 |
| 对象存储 | `DriveStorage.java:291` | `deleteDirectoryTree`：先分页收集子目录标记对象再删（边翻页边删会让 `continuationToken` 指向已变动的结果集），**文件对象一个不碰** |
| Go Core | `internal/drive/client.go:359`、`app.go:1608` | `DeleteTree`；`CloudDelete` 按键形分派——目录键（带尾斜杠）走递归。绑定签名未变，不必重生成 TS 绑定 |
| 前端 | `CloudPanel.vue:300`、`App.vue:105` | 拒绝改为确认：把「其中几个文件、几个子文件夹」报给确认框（目录标记也在清单里，按尾斜杠分开数，否则子文件夹会被说成文件） |

顺序刻意是**先软删文件行、再清目录标记**：反过来中途失败会留下「标记没了、文件还在」的孤儿目录。

**目录本身不进回收站**——它没有 `es_file` 行（与 mkdir「刻意不建行」同口径，避免污染秒传判定）。
还原任一子文件时目录按路径段重新出现，因此不需要目录的回收站态。

## 验证

活栈端到端（PG 16 + Redis + RustFS + 本机控制面 8090，脚本
`scripts/diag/recursive-delete-check.mjs`，造 `rectest/a.txt` + `rectest/sub/b.txt` + 两个空目录标记）：

```

PASS  删除前子树齐备
PASS  递归删后目录与子目录标记全部消失  — 无残留
PASS  两个子文件都进了回收站
PASS  还原后文件回到原路径
PASS  还原出来的内容仍可读  — 读回 "A"
PASS  目录标记不复活（按路径推导，不进回收站）
PASS  非递归删只摘标记、子文件不动
```

最后一条是本片刻意保留的边界：不带 `recursive` 的删除只摘目录标记，子文件不动——
WebDAV 与挂载盘走的就是这条路，行为不变。测试数据已全部清理（`rectest`/`otherdir` 无残留）。

回归：Java `mvn clean test` **90 用例全绿**（原 88，+2：子树软删逐行落回收站并逐条记 `deleted`

与钉盘的 `deleteDentry` 单次调用相比是已知差距。

## 同日第二片：资源管理器里的目录要上云

审计「学到 → 落地」时发现同类缺口的另一处：**目录只在挂载盘本机记着**。
`internal/spacedav/spacedav.go` 的 `Mkdir` 只写进程内存 `pendingDirs` 与本地 `dirs.json`，
从不调控制面 `/mkdir`（该端点与网盘页同日落地）。后果是「此电脑里新建的文件夹」
只有这台机器看得见——网盘页没有、换台电脑没有、共享空间的同事更没有。
反向也不对称：`RemoveAll` 摘掉本机记录，却不摘服务端标记，网盘页于是长期挂着
一个「本机已删」的空文件夹。钉盘/WPS 的目录是云端实体，任何一端建了所有端一致。

改动（都在 `internal/spacedav/spacedav.go`）：

- 新增可选能力接口 `mkdirClient`（与既有 `changeClient`/`fileIDDeleter` 同一模式），
  `Mkdir` 记完本机再向控制面建标记。
- `RemoveAll` 判明是目录后用带尾斜杠的路径删标记——服务端那条分支只摘标记、不动子对象。
- **两处都刻意不报错**：未登录、旧控制面没有 `/mkdir`、旧服务端不认尾斜杠删除都会失败，
  这时退化为「仅本机可见」，而不是让资源管理器弹「拒绝访问」。
  代价写在注释里：控制面没部署到位期间，这台机器新建的目录在别的端仍不可见。

**验证**：新增活栈用例 `TestLiveSpacedavDirectoryIsCloudEntity`（真实控制面 + RustFS）——
WebDAV `Mkdir` 后 `GET /objects?includeDirs=true` 能看到 `…/cloud-dir-<纳秒>/` 标记；
放入子文件后 `RemoveAll`，服务端在用清单里**子文件与标记同时消失**，测试数据零残留。
`internal/spacedav` 其余 3 条活栈用例（读写改名往返 / Range 随机读 / 冲突副本）同批通过；
新增 6 条单测覆盖「无服务端能力也能建」「控制面失败降级」「只读空间不碰服务端」
「删文件不会误发 `a.txt/`」。`go build ./...` + `go test ./...` 全绿。

## 同日第三片：「始终保留」与「释放空间」

WPS 取证 §0b 第四步与 §3.5 的 `freeUpPlaceholder` / `KCfApiSyncFolderFreeUpHandler`
是两家桌面形态最标志性的两个开关，也是切片 5 唯一还缺的一环（此前只有 FETCH_DATA 与
CANCEL_FETCH_DATA 两个回调，状态位只有 in-sync 一层）。

**动手前先纠了一个会咬人的编号错误**：`internal/cfapi` 的 `CallbackType` 常量此前抄自
WPS 取证 §2.1b 里从 `ksyncengine.dll` 读出的回调表（0/2/6/9/11）。数字没读错，**名字错了**——
那套编号是 WPS 自己编译期 SDK 的枚举顺序。按本机
`Windows Kits\10\Include\10.0.26100.0\um\cfapi.h`（第 488–503 行，枚举自 0 顺序编号）：
`6 = NOTIFY_FILE_CLOSE_COMPLETION`、`7 = NOTIFY_DEHYDRATE`、`9 = NOTIFY_DELETE`、
`11 = NOTIFY_RENAME`。也就是说旧写法 `CallbackTypeNotifyDehydrate = 9` 一旦真去订阅，
订到的是删除通知，永远收不到释放空间的回调。当前订阅表只用 0 与 2（新旧一致），
所以**还没造成故障**；常量已按 SDK 全量重写并逐项标注，取证文档的编号对照需同步更正。

改动：

- 新增 `internal/cfapi/state_ops_windows.go`：`SetPinState` / `Dehydrate` / `Hydrate`，
  枚举与原型逐字取自上面那份 SDK 头。
  句柄用 `FILE_READ_ATTRIBUTES | WRITE_DAC` 打开——SDK 要求「READ_DATA 或 WRITE_DAC」二选一，
  而带 READ_DATA 打开占位符**会直接触发水合**（本包既有实测），
  让「释放空间」先把文件下载回来是彻底自打脸。
- `cfmount_app_windows.go` 新增 `CloudKeepOnDevice` / `CloudFreeUpSpace` 两个导出方法，
  云端路径 → 同步根本地路径的映射带三道闸（已挂载、非绝对路径、无 `..` 段、
  拼接结果必须仍在同步根内）。非 Windows 平台在 `cfmount_app_other.go` 返回明确错误
  而非静默成功。
- 前端：网盘右键菜单加两项，仅在本机挂载占位符时出现；`wails generate module`
  重生成绑定并同步 `services/core.ts`。
- 「释放空间」刻意先解除钉住再脱水：平台**拒绝**对已钉占位符脱水，
  直接调用用户只会拿到一个看不懂的 HRESULT。

**真机验证**（`internal/cfapi/state_ops_windows_test.go`，本机 Windows + cldapi）：

```
--- PASS: TestPinAndDehydrateRoundTrip        30 KiB 占位符
      分配 0 → 读后分配 30030 → 钉住 → 脱水被拒（0x80070188，分配量未变）
      → 取消钉住 → 脱水成功、分配回到 0 → 再读内容逐字节一致且重新触发一次按需取数
--- PASS: TestSetPinStateOnDirectoryRecurses  对目录带 RECURSE 位成功，
      其子文件随后脱水被拒——证明递归位真的生效
```

回归：`go build ./...`、`go test ./internal/cfapi ./internal/cfmount -count=1`、
`go test ./...` 全绿；`vue-tsc --noEmit` 干净、vitest 45 全绿。

**边界**：资源管理器里那两个系统自带的菜单项是否已经出现，**没有点验**（本会话无法驱动
桌面窗口）——按 SDK 说明 `CfSetPinState` 任何进程都能调、shell 的动词走的就是同一套内核接口，
但这是推断不是实测。应用内的两个入口同样未真机点验。
Explorer 动词若需要提供方应答 `NOTIFY_*` 回调才生效，则还要补订阅表（本机编号 7/8 已就位）。

## 同日第四片：占位符挂载改吃增量列举，并修掉一个 FFI 边界崩溃

钉盘 §4 那套「空间版本 + 变更流水」此前只有 WebDAV 挂载在吃，
按需占位符的同步根**每 5 分钟仍是一次全量列举**（`cfmount.List` 调 `Objects`）。
万级空间下这就是一次全量拉取 + 全量对账，等于把学到的协议只落地了一半。

### 改动

| 位置 | 做了什么 |
| --- | --- |
| `internal/drive/changes_apply.go`（新） | 增量合并从 `internal/spacedav` 上收到 `drive`：`ApplyChanges(base, changes)`。两个消费方共用一份语义，**有两份实现迟早分叉**，分叉的后果是同一个空间在两个入口里内容不一样。复制动作也在里面，调用方不必自己先 copy |
| `internal/cfmount` | 新增可选接口 `ChangeLister` 与跨调用状态 `ListState`；`Config.State` 传了就走 `/changes`（首轮不带游标 = 全量重建，之后带空间版本只问差异），没传或旧控制面失败都**完整退回全量**，行为与改动前一致 |
| `cfmount_app_windows.go` | 增量状态挂在挂载上，挂载与定期同步共用一个实例；卸载/换账号时置空——**换账号沿用上一个账号的游标会漏事件** |

游标只在内存里、刻意不落盘，理由写在 `ListState` 注释里：跨进程重启后第一次必然是全量
（底没了），落盘的版本号在那一刻用不上；而**与 WebDAV 挂载共用一个版本文件是危险的**——
两个消费方各自维护视图，共用会让一方把另一方的游标推前，另一方再去要差异就漏掉中间的事件。

### 顺手抓到一个真机缺陷

`Change.LastModified()` 在服务端没带时间（或时间串解析失败）时返回 `time.Time{}`，
而 `.Unix()` 是 **-62135596800**；`TimeToFiletime` 直接换算就得到**负 FILETIME**，
内核用 `E_INVALIDARG (0x80070057)` 拒绝整条 `CfCreatePlaceholders`——
症状是「云端新建的文件在本地建不出占位符」。增量事件流本来就允许只带身份不带时间，
所以这不是假想场景，是这条链路上必然会发生的一次失败。

两处一起修：`cfmount` 侧零时间落成 cfapi 约定的 `0`（未知），
`cfapi.TimeToFiletime` 对 `<= 0` 一律当未知处理（FFI 边界自己兜住，别把负数递进内核）。

### 验证

- `internal/drive/changes_apply_test.go`：6 条——created 带元数据、updated/restored 不覆盖既有 size
  （否则用户看到文件「变小」）、moved 保留元数据并换路径、deleted/purged 移除、
  **输入切片不被改写**、未知事件原样返回。
- `internal/cfmount/incremental_windows_test.go`：4 条——首轮不带游标、次轮带版本 7、
  走增量后**一次都不该用旧的全量接口**、控制面不支持时三轮都完整退回全量且不带游标。
- `internal/cfmount/incremental_sync_windows_test.go`（真机 CfApi）：
  差异事件真的建成占位符（逻辑大小 11 是云端值）、没人读它就一次都不拉内容、
  读它才拉到正确字节且只拉那一个。
- `internal/cfmount/live_mount_windows_test.go`（**活栈 + 真机**）：真实控制面上传两个文件，
  挂载 + 同步两轮，断言 `objectsCalls == 0`、次轮游标是服务端真实空间版本、
  第二个文件经服务端变更事件落成本地可读占位符。测试数据已清（`live-cfmount` 零残留）。
- `go build ./...`、`go test ./...` 全绿；`go test ./internal/cfmount ./internal/cfapi -count=1` 真机全绿；
  `internal/spacedav` 改用共享合并实现后其既有单测与活栈用例全部保持通过。

**边界**：mtime 缺失时占位符会显示 1970 前（FILETIME 0 = 1601 年）而不是编一个假时间——
与目录条目的既有口径一致。真实控制面对 created 事件是会带 `lastModified` 的，
这条只在旧服务端或时间串格式变化时暴露。

## 同日第五片：按需取数的进度回报（切片 5 第 3 步欠的那半）

**先说一个被我否掉的计划**：原本排在这轮的是路线图第 7 步「本地元数据表」。
读代码后确认它现在不值得做——挂载是只读的，本地不可能发生改名/移动，
那张表的用途（`cloudFileId ↔ fsFileId` 双向绑定）是给双向同步用的；
而现在怀疑的「身份从路径哈希翻成 fileId 会导致占位符重建」也不成立：
`tree_windows.go` 对已存在的条目走 `updateExisting` → `UpdatePlaceholder(h, meta, e.Identity, ...)`，
**身份是原地更新的，内容与钉住状态都不丢**。为假想需求先铺一层持久化，正是本仓明令不要做的事。

于是改做 WPS 桌面形态里真正缺的那半：大文件点开时的**可见进度**。
本包取数是同步回调，回调占多久用户就等多久，此前没有任何回报——
用户看到的是一个既不报错也不动的窗口。

### 改动

- `internal/cfapi/progress_windows.go`（新）：`CfReportProviderProgress(连接键, 传输键, 总量, 已完成)`，
  原型逐字取自本机 SDK 头 `cfapi.h` 第 1143–1149 行。**参数顺序是先总量后已完成**，
  写反不报错、只会让进度条一直 0%——这一点在注释里点名了。
- `FetchRequest` 带上 `ConnectionKey` / `TransferKey`（内核标识），`onFetchData` 填。
- `mount_windows.go`：`io.ReadFull` 换成 `readProgressively`，每读满 1 MiB 回报一次；
  **总量低于 8 MiB 不回报**（内核在这个量级根本不弹进度框，回报只是纯开销）。
- `SetProgressObserver` 是**旁路观察**而不是替代：内核调用照常发生。
  若挂上钩子就跳过真调用，「参数顺序对不对」在测试里永远不会被执行到，
  而它错了的症状恰好是静默不动。为此另加 `ProgressFailures()` 把被内核拒绝的次数露出来。

### 两个真机抓到的问题（都不是推理出来的）

1. **进度回报写全了却没生效过**：第一版把观察钩子做成「替代内核调用」，
   真调用一次都没跑过。改成旁路 + 失败计数后，用例才能断言「内核接受了我们的回报」。
2. **`readProgressively` 把「最后一块字节与 `io.EOF` 同时到达」当失败**：
   HTTP 响应体这类 reader 就是这个行为，`io.ReadFull` 对此返回成功。
   症状很硬：cfmount 的 Range 集成用例里 18 字节的占位符读不出来，
   回调整次失败，用户侧等到内核超时（121 秒后报「云操作未在超时时间内完成」）。
   修法是判满即成功，并且**先回报再判满**——顺序反了会把读满那一刻的回报吞掉。

### 验证

真机（本机 CfApi + 12 MiB 内存源，64 KiB 一块喂进去）：

```
回报 12 次，首 1048576 / 末 12582912（总量 12582912），读满 12582912 字节
ProgressFailures() == 0    ← 每一条都被内核接受，证明参数顺序与键都对
```

另有 4 条纯逻辑用例钉住 `readProgressively`：每块都报、短读在 EOF 处停、
不带回报时等价普通读、**最后一块带 EOF 必须算成功**（回归）。
`go test ./internal/cfapi ./internal/cfmount ./internal/drive ./internal/spacedav -count=1`
与 `go test ./...` 全绿；`go vet` 干净。

**边界**：进度只在**单次请求区间 ≥ 8 MiB** 时回报；内核把一个文件拆成多个小区间时，
每个区间都不回报是正确行为（用例遇到这种情况会明确 skip 而不是假装通过）。
至于系统把进度画成什么样子（百分比还是字节数），是内核的显示逻辑，不在本包可验证范围。

### 接上闸门之后当场抓到的四件事

1. **`docs/architecture.md` 有一条误报**：`GET` / `POST` 那行的 `` `/api/mcp/info` · `/api/mcp/regenerate` ``
   被判成「文件不存在」。**没有改文档去迁就脚本**——文档写的是接口清单，本来就是对的；
   错的是检查器的口径。规则收成「两边都以 `/` 开头即路由枚举，不是文件引用」，
   并把它做成自检用例（`路由并排必须跳过`），防止以后有人为了消除红点把真引用也跳过。
2. **自检当场抓到我自己写错的一条用例**：注入「符号改名」那条时字符串里多了 `\`` 转义和一个句点，
   正则没匹配上，期望失败 1 实得 0——**闸门差点对自己失效**。这就是写自检的全部理由。
3. **`--apply` 类脚本不能当闸门**：`color-literals.mjs` 永远退出 0，它是给人看的报告；
   真正的红线在 `designTokens.test.ts` 里。文档里把两者分开写清楚，避免下次误以为「跑过脚本＝有闸门」。
4. **两条「文字被吃掉」的空链接**：`docs/intelligence/` 两篇警示块里各有一条 `[](../benchmark-absorption.md)`，
   渲染出来是一段**看不见的空文本**——是我此前用 shell 改这两篇时产出的（当时只核了行数与标题，没核链接文本，
   所以漏过去了）。两条重复警示已删，检查器随即补上 `scanEmptyLinkText` 规则，全仓现有空链接文字计数 = 0。
