# TencentDB-Agent-Memory 对标学习：分层记忆、资产治理与按需知识

> 日期：2026-08-20
> 状态：已完成（纯调研，无代码变更）
> 研究基线：[TencentCloud/TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory) `97f94654280b`（v2.0.1-beta.1，MIT，Node.js ≥22）

## 1. 用户问题

知识平台即将进入 1.9 混合检索加固（Agent 多跳检索），远期还有知识原子萃取、知识有寿命、权限感知检索与 WPS 知识副驾驶。这些方向目前只有我们自己的判断，需要一个已获规模验证（2 万+ star、腾讯云数据库团队出品）且技术栈高度重合（BM25+向量+RRF 融合、SQLite、LLM 异步提炼管线）的开源参照系，检验路线并对齐 API/数据模型设计。

定位差异先说清：它是"给 Agent 团队的记忆中枢"，我们是"给企业的知识平台"——企业知识恰恰是 Agent 记忆最重要的上游，两者是互补关系而非竞品。

## 2. 目标

- 吃透其四组件架构与 L0-L3 分层记忆模型。
- 找出对 1.9（多跳检索 API 形态与检索策略）、里程碑 2（资产治理元模型）、里程碑 3（副驾驶注入策略）的可落地借鉴。
- 明确不照搬边界，防止"看到好东西就搬"。
- 结论沉淀到本文档，供 1.9 设计阶段直接引用。

## 3. 非目标

## 5. 核心发现

### 5.1 产品论点与我们高度共振

它的口号"已有信息 → 可复用记忆资产 → 更少 Turns → 更少返工"，以及"RAG 解决'能查到什么'，Team Memory 还要解决'谁可以用、哪个版本有效、应该给哪个 Agent'"——几乎就是 [`knowledge-platform.md`](../knowledge-platform.md) §1.2「知识原子 / 知识有寿命 / 知识找人」的另一种表述。**方向验证：EasyShare 押注"超越普通 RAG"的路线与行业头部实践一致。**

### 5.2 四组件与职责切分

| 组件 | 端口 | 职责 |
| --- | --- | --- |
| MemoryCore | 8420 | 记忆内核 + 元数据：L0-L3 存储、Skill/资产元信息，SQLite |
| MemoryKnowledge | 8421 | 内容引擎：Wiki 解析/索引/检索、CodeGraph 构建 |
| MemoryPanel | 8123/8125 | 治理操作台：资产审核、分享、Agent 配装 |
| MemoryProxy | 8096 | 透明 LLM 代理：会话初始化、上下文注入、对话回流、计费 |

**关键切分：MemoryCore 只存 Knowledge 元信息（标识/类型/状态/关联/service_url），不存内容；内容由 MemoryKnowledge 处理。** 这与我们"Java 控制面管谁能看、Python 计算面管内容向量"的架构切分同构——里程碑 2 的方向获得独立验证。

### 5.3 L0-L3 分层模型：知识原子的先行实现

对话先存 L0，再由异步 Pipeline 逐层提炼：

| 层级 | 内容 | 用途 |
| --- | --- | --- |
| L0 Conversation | 原始对话与完整上下文 | 核对原话、时间和来源 |
| L1 Atom | 事实、偏好、约束与事件 | 精确召回可执行信息 |
| L2 Scenario | 围绕项目/场景组织的知识块 | 快速恢复工作场景 |
| L3 Core/Persona | 长期画像、稳定模式 | 迅速进入用户和团队语境 |

对 EasyShare 的三点启示：

- **L1 Atom 就是"知识原子"的实现形态**（事实/规则/流程/定义 + 出处），证明该层可以工程化。
- **生成溯源做到提取过程级**：每条 L1-L3 记录实际使用的 Prompt ID、版本、来源、SHA-256 与输入输出引用，可按 Memory ID 反查生成日志。我们的驾驶舱"生成审计"覆盖了答案侧，将来知识原子落地时应把溯源延伸到提取侧。
- **其 v2.0.1 路线图承认"自动抽取的记忆不会永远正确"**，为此加 L1-L3 人工可编辑。印证"知识有寿命"路线的判断：追求抽取 100% 正确不现实，给人修正/废止入口更现实。

### 5.4 分层召回 + 预算控制

原文："平时用 L2/L3 快速进入语境，需要具体事实时通过 BM25、向量检索与 RRF 回到 L1/L0。结果还会经过条数、字符预算和超时限制，避免记忆反过来占满上下文。"

→ 1.9 检索策略的设计原则参考：召回不只是"排序对"，还要"层级对 + 预算受控"。多跳检索尤其需要预算约束，否则每跳结果叠加会雪崩式膨胀上下文。

### 5.5 按需知识：tools/list + tools/call 两步自发现

Agent 先 `POST /v3/tools/list` 发现知识能力（Wiki 页面检索、CodeGraph 查询等），再用 `/v3/tools/call` 按需读取页面、源码或影响路径。文档和代码平时只是"可用的工具"，真正需要时才进上下文。

MCP 接入方式值得注意：`MemoryKnowledge/src/mcp/` 用 **stdio→HTTP 转发的薄桥**，而非原生实现 MCP 协议。

→ 1.9 Agent 多跳与「MCP 基础设施」愿景的 API 形态参考：FastAPI 已有完整 HTTP API，加薄 MCP 桥即可对外成为 MCP Server，不必原生实现协议。

### 5.6 注入 vs 工具化（Proxy 的生产级洞察）

| 层级 | 接入方式 |
| --- | --- |
| L2/L3（稳定画像） | 直接注入 system prompt |
| L0/L1（易变事实） | 以只读工具暴露给模型按需查询 |

理由："避免破坏上游 KV cache"——注入内容频繁变化会导致前缀缓存失效，token 成本翻倍。这是生产环境换来的洞察。

→ 里程碑 3 WPS 副驾驶 Just-in-Time Context Loading 的注入策略：稳定上下文进 prompt，易变事实走工具，兼顾效果与成本。

### 5.7 工程韧性模式（细节里见成熟度）

- **BM25 降级**：未配置 Embedding Provider 时默认 BM25 召回，核心功能不因外部依赖缺失而不可用。
- **存储降级链**：cos → sqlite → fs → memory，任一后端失败自动降级，`/health` 暴露 `storage.effective` 作观测锚点。
- **三路独立可观测**：Opik / Langfuse / ClickHouse 互相独立，任一失败不影响业务；`tool_call_logs` 记录每次工具调用的 user/team/agent/turn 维度，正文脱敏并截断。
- **"租户调策略、平台冻契约"**：L1/L2/L3 提取 Prompt 按 `Agent > Team > Instance > 系统内置` 优先级可自定义，但固定输出协议（L1 JSON / L2 Markdown / L3 Persona）不可改。与我们的清洗规则引擎"规则集为 JSON 数据、租户下发同一 schema"是同一哲学，获得验证。
- **Benchmark 纪律**：PersonaMem 基准有无对照（48% → 76%），与驾驶舱"数据驱动选型"的方法论一致。

## 7. 借鉴建议（按优先级）

### P0 —— 并入 1.9 设计（全部是设计决策，实施成本≈0）

1. **检索结果预算控制**：条数 / 字符 / 超时三上限进入 `/query` 与多跳设计，防止多跳上下文雪崩。
2. **多跳 API 采用两步自发现形态**（能力发现 + 按需调用）；MCP 用 stdio→HTTP 薄桥实现，不原生实现协议。
3. **无 Embedding 时 BM25-only 降级模式**：离线开发与供应商故障时核心检索仍可用，符合"开箱即用"哲学。
4. **QueryLog 细化到 hop 级**：多跳落地时记录每跳的 query/策略/结果数/是否被答案引用，健康度仪表盘的"使用率"从查询级升级为知识级。

### P1 —— 里程碑 2 前吸收进设计文档

5. **资产治理元模型参照**：知识资产登记（id/type/status/关联/service_url）与内容分离；可见性分四级（私有/团队/ACL 授权/定向装配）。
6. **提取阶段生成溯源 + 人工校准入口**：知识原子记录"由哪个 prompt 版本从哪个 chunk 提取"；驾驶舱支持编辑/废止，不追求抽取 100% 正确。
7. **租户可调提取策略、平台冻结输出 schema**：自定义关注点可下发，原子数据结构不开放修改。

### P2 —— 里程碑 3 前再回头看

8. **副驾驶注入策略**：稳定上下文注入 prompt、易变事实走工具调用（KV cache 洞察）。
9. **Wiki 式场景页**：原子知识按业务场景组织成 LLM 增量维护的页面（可复利资产），而非只有 chunk 列表——灵感源自 Karpathy 的 LLM Wiki，TDB-AM 已工程化。
10. **`mem:` 式轻量指令 UX**：一行指令触发知识操作（同步/存记忆），副驾驶交互可参考。

## 8. 不照搬边界

- **不引入其代码或服务作为依赖**：清洗规则引擎、驾驶舱、黄金语料评测集是我们的核心资产，替换即损失。
- **不做多 Agent Team / Loadout / Persona 编排**：那是 agent-workforce 问题域，企业知识平台不背这个。
- **CodeGraph / Skill 不进产品路线**；CodeGraph 若将来作开发工具评估，另行立项。
- **不学其 Proxy 透明代理模式**：它绑定"客户端可控 base URL"的前提，WPS 插件场景我们直接走服务端 API，不需要中转层。
