# ADR-0001：文件身份、目录树与版本模型

- 状态：提议
- 日期：2026-07-19
- 决策者：EasyShare maintainers
- 关联：[`../product-vision.md`](../product-vision.md)、[`../technical-selection.md`](../technical-selection.md)

## 背景

路径会因重命名、移动、大小写变化和父目录变更而改变，不能作为云端文件身份。同步、分享、版本历史、回收站和内网加速都需要在路径变化后继续引用同一个逻辑文件。文件内容也可能被多个版本或条目引用，不能与目录条目混为一体。

Windows 默认大小写不敏感，但对象存储 key 和其他客户端可能区分大小写；如果不在服务端统一定义名称规则，不同设备会看到不可同步的目录状态。

## 决策

云端元数据使用 PostgreSQL，并分离三个概念：

1. **FileEntry**：目录树中的逻辑文件或目录；
2. **FileVersion**：文件一次不可变的内容版本；
3. **ContentObject**：对象存储中的不可变内容。

建议的最小字段如下，最终以数据库设计评审为准：

```text
FileEntry
- id                 UUID/UUIDv7
- drive_id           所属个人盘或空间
- parent_id          根目录为 null
- name               原始展示名称
- normalized_name    用于唯一性判断
- kind               file | directory
- current_version_id 文件可有，目录为空
- revision           元数据乐观并发版本
- deleted_at         墓碑时间
- created_at / updated_at

FileVersion
- id
- file_id
- content_id
- size
- content_hash
- base_version_id
- created_by_device_id
- created_at

ContentObject
- id
- storage_key
- size
- hash_algorithm
- content_hash
- state
- created_at
```

采用以下语义：

- `file_id` 在重命名和移动后保持不变；
- 路径由父链和名称派生，不作为外键或远端身份；
- 文件内容更新创建新的不可变 `FileVersion`；
- 移动、重命名等元数据变更增加 `revision`，但不伪造内容版本；
- 删除首先写入墓碑和变更日志，经过保留期后才做物理清理；
- 同一有效父目录内，`normalized_name` 必须唯一；
- API 中涉及更新的操作必须携带调用方已知的 revision 或 base version；
- 对象存储 key 使用不透明标识，不使用用户文件路径；
- 内容哈希记录算法，首选 SHA-256，不把 S3 multipart ETag 当作内容哈希。

名称规范化的精确算法需要通过跨平台和数据库实验后冻结；第一版至少必须拒绝 Windows 不可表示的名称、保留名和同目录大小写碰撞。

## 不变量

1. 任意有效条目只有一个稳定 `file_id`。
2. 任意已提交版本指向不可变且已验证的内容对象。
3. 重命名和移动不改变 `file_id`。
4. 用户路径不进入对象存储 key，也不作为同步游标。
5. 删除、恢复、移动和版本切换都产生可增量获取的变更。
6. 客户端不能仅凭自己提供的哈希获得无权限内容。

## 备选方案

### 以路径作为主键

拒绝。移动目录会导致所有后代身份变化，离线并发时也无法判断“移动”还是“删除后新增”。

### 每次修改生成新的 file ID

拒绝。分享链接、同步绑定、版本历史和内网来源都无法稳定引用逻辑文件。

### 文件条目和内容对象合并

拒绝。会迫使重命名复制内容记录，也难以表达版本历史和安全的内容复用。

### 使用对象存储目录作为元数据数据库

拒绝。对象存储不提供所需的目录事务、名称唯一约束、乐观并发和可靠变更日志。

## 影响

正面影响：

- 重命名和移动可被准确表达；
- 版本、回收站、分享和内网加速可以复用同一身份体系；
- 对象内容可以独立校验和清理。

成本与风险：

- 需要维护目录约束和墓碑生命周期；
- 名称规范化必须兼容 Windows；
- 内容对象清理需要引用检查，不能在删除条目时直接删除对象。

## 开放问题

- 个人盘之外是否需要团队空间和租户 ID；
- 版本保留数量和时长；
- Unicode 规范化采用 NFC、数据库 collation 还是应用层生成规范键；
- 是否允许目录条目拥有独立 revision 历史；
- SHA-256 是否同时配合 BLAKE3 作为本地快速指纹。

## 验证

数据库和 API 实现前至少覆盖：

- 文件与整个目录重命名后 ID 不变；
- 大小写冲突和 Unicode 等价名称；
- 两台设备并发移动/重命名；
- 删除后修改、恢复后再次同步；
- 相同路径删除后重建时获得新的 file ID；
- 内容对象仍被历史版本引用时不会被清理。
