# EasyShare 清洗规则引擎：结构噪声 + PII 脱敏 + 自定义规则

日期：2026-07-27 · 主题：把清洗环节从硬编码薄层升级为可配置、可追溯、可被控制面接管的规则引擎

## 用户问题

- 企业文档带大量结构噪声（页眉页脚、页码、水印），直接入索引污染检索；
- 合规场景需要对手机号、身份证、邮箱、地址等敏感信息做脱敏，且不同部署的开关需求不同；
- 即将接入的 OCR 输出噪声更重，没有规则引擎等于把脏水灌进索引——因此本迭代先于 OCR 落地。

## 目标

- 规则引擎作为解析后的独立管线阶段：结构噪声规则（默认开）+ PII 脱敏规则（默认关）+ 自定义 regex 规则。
- 规则集是可序列化 JSON 数据（`data/cleaning_rules.json` 覆盖内置默认），里程碑 2 起 Java 控制面按租户下发同一 schema，Python 端零改动。
- 可追溯：manifest 记录每条启用规则的命中次数（`cleaning.rules[]`），清洗前后可对账。
- 外部规则执行防护：正则长度上限 200、规则数上限 100、编译失败/坏配置降级为警告并跳过，不中断管线。
- `GET /cleaning/rules` 只读查询当前生效规则集。

## 非目标

- 不做规则管理 UI 与租户级配置（里程碑 2 Java 控制面职责）；
- 地址识别不追求 NER 级精度：正则版误伤率高，标注为实验性且默认关；
- 不改变 `parse_document` 的纯解析语义——黄金语料测试口径不受规则引擎影响。

## 设计决策

- **执行在 Python、治理归 Java**：清洗在计算面管线内部执行；"用哪套规则"是控制面策略。规则定义为 JSON 数据而非代码，未来配置来源从本地文件换成请求参数即可，两端不返工。
- **两类规则区别对待**：结构噪声（页眉页脚/页码）提升检索质量，默认开；PII 脱敏伤问答召回（"张三电话多少"将不可答），是业务决策，默认关、按需开。
- **管线级挂载而非解析器内部**：`DocumentPipeline` 在 `parse_document` 之后调用 `RuleEngine.apply`，报告写 manifest；golden 测试继续只测纯解析，评测集语料（无分页、PII 关）不受影响。
- **页眉页脚用跨页频率检测而非正则**：同一短行（≤60 字符）出现在 ≥max(3, 60% 页数) 个不同分页上即整块删除；不足 3 页不启动，避免误伤短文档。
- **页码规则限定分页文档**（`params.pages_only`）：独立数字行只在带 `source.page` 的块里删除，纯文本文档中的孤立数字不受影响。
- **脱敏保留业务可用性**：手机号 `138****5678`（保 3+4）、身份证 `110101********863X`（保行政区划+校验位）、邮箱保域名遮本地部分——保留辨识度而非全删。

## 兼容与迁移

- manifest 新增 `cleaning` 字段（additive），`PIPELINE_VERSION` 升至 `2026-07-27.1`；旧 manifest 读取不受影响（响应模型可选字段）。
- 新配置 `CLEANING_RULES_PATH`（默认 `./data/cleaning_rules.json`），无文件时行为 = 内置默认 ≈ 旧版清洗 + 分页噪声清除。
- 黄金语料、检索评测集全部不受默认规则影响（已验证）。
