## 开工依据

三层路线在角色片已由用户选定（「要像钉钉这样精细化」→ 三层路线）；本会话长期目标指令「多次迭代多次完善」。设计稿参数经钉钉对标校准后直接落实现，**未提交推送仍待用户明确指示**（AGENTS.md 约定）。

## 目标

1. 共享空间文件支持**成员级四档角色**：manage（可管理）/ edit（可编辑）/ download（可查看下载）/ read（仅可查看），服务端真实拦截（不藏按钮）。
2. 裁决一处收口：列表过滤、下载签发、删除、改名、覆盖上传、授权端点全部走同一份梯子。
3. 两条护栏对齐钉钉：**不能修改自己的角色**、**仅上传者/manage 档可授权**。
4. 兼容前提：未配任何成员角色的文件，行为与本片引入前**完全一致**。

## 设计决策（实现与设计稿的差异回填）

### 1. 默认档修正：空间 write 成员默认 manage，read 成员默认 download

设计稿写的是「默认 download」，实现时按行为对账修正：今天共享空间 write 成员可以**删除/改名任何文件**（`checkSharedWritable` 一道门），如果默认压到 edit/download，这批人的既有能力会被静默收窄。因此梯子第 4 级为：write 成员 → manage、read 成员 → download——**未配角色的文件行为零变化**；显式成员行才有收窄/提权效果。

### 2. visible_depts 语义修正：命中 = download 档

设计稿写「visible_depts = read 档简写」，同样修正：今天部门命中即可见**且可下载**（`assertDownloadable` 只查可见性），映射成 read 会砍掉存量部门的下载能力。修正为 download 档——语义与引入前完全一致；「仅预览不下载」的收窄从成员行开始才有。

### 3. 共享空间没有「空间所有者」主体

设计稿提到空间所有者隐式 manage；实现发现共享空间是**单例**（`es_file.owner_id` 恒 0），没有个人所有者。隐式 manage 只有**上传者**（`upload_by`，与今天「上传者可改可见范围」的既有行为同源，升为全权）。存量补账行 `upload_by=0` 不认上传者，防「全网上传者」。

### 4. 删除收为 manage 独占（对齐钉钉），改名/覆盖上传 edit 起步

钉钉的可编辑档不含删除（`workspace_editable_tip` 可新建/导出/打印/查看/编辑，无删除）。接线：

| 动作 | 端点 | 门槛 | 未登记行 |
| --- | --- | --- | --- |
| 下载/预览签发 | `POST /easyshare/drive/presign-get` | ≥ download（read 档明确报「仅可在线预览，不能下载」） | 不拦（与列表口径一致） |
| 删除 | `DELETE /easyshare/drive/object` | **manage 独占** | 不拦（目录标记/幽灵行沿用空间级写权限） |
| 改名/移动 | `POST /easyshare/drive/move` | ≥ edit | 不拦 |
| 覆盖上传 | `presign-put` + `upload-session/create` | ≥ edit（新路径无行不拦，建新文件走空间级写权限） | 不拦 |
| 改可见性 | `POST /easyshare/drive/file-visibility` | 上传者恒可，其余 manage | — |
| 授权 | `GET/PUT/DELETE /easyshare/file-member/...` | manage 独占 | — |

### 5. 整组替换时授权者自己的行原样保留

显式拿到 manage 档的成员整组替换成员行时，若把自己也刷掉就再也无法管理。实现为：删除旧行前记下操作者的既有用户行，重插回（请求里出现自己的行仍被拒绝——不能修改自己的角色）。上传者是隐式 manage 不受行影响，同样拒绝自改，口径只有一条。

## 已知边界与后续切片

1. **授权入口仅超管可用**：UI 卡放在管理页「空间」Tab（超管可见），成员/部门下拉复用管理页数据源。非超管的 manage 档成员（如文件上传者）暂无 UI 入口，可走 API；钉钉式「网盘页右键 → 成员角色」需一个普通用户可调的成员搜索端点，留下一片。
2. **安全开关（防复制/水印）未做**：按设计稿划出本片，挂 `es_space` 留下一片。
3. **知识检索零改动**：`/query` 的 `visible_doc_ids` 口径不变——成员行授权的「read 及以上可见」与今天 visible_depts 的可见性语义一致；若将来要「read 档文档不可入检索索引」再联动。
4. **动作枚举不展开**：我们的文档动作只有六个，逐动作建模是过度设计；钉钉 67 项动作枚举留档（intelligence 文档），API 面变密再对齐。

## 真机点验清单（下次省事）

需要控制面重部署（含 `easyshare-file-member.sql`）+ 桌面端重装：

1. 空间 write 成员对未配角色文件：上传/改名/删除/下载全部照旧（兼容基线）。
2. 管理页「空间」Tab「文件访问角色」卡：选文件（fileId 字符串下拉）→ 载入已有行 → 添加成员行（账号/部门 + 四档）→ 保存；重复主体报「该成员已有角色行」。
3. 管理员（上传者）给成员 B 设 `download`、C 设 `read` → C 看得到文件但下载报「当前权限仅可在线预览，不能下载」；B 可下载；C 调 presign-get 返回同一文案。
4. C 尝试删除该文件 → 「只有可管理权限的成员可以执行此操作」；B 改名 → 同样被拒（edit 起步不含删除——B 是 download 档更不行）。
5. 给被 visible_depts 排除的成员 D 显式授 `read` → D 能看到文件（成员行授予可见性）。
6. 授权端点：非 manage 档调用 403 语义错误；管理员把自己 userId 放进请求 → 「不能修改自己的角色」（下拉里已排除自己）。
7. 删文件 → `es_file_member` 无孤儿行（psql 查 file_id）。
