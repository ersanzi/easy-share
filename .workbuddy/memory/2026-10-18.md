## v0.3.2：装完仍连本地 + macOS 打包失败（用户报「下载安装后还是调用本地地址，mac 打包还是有问题」）

用户口径：v0.3.1 装完仍调本地地址，且 macOS 打包仍失败。两个问题根因完全不同。

### ① 「装完仍连本地」不是 CI 的锅，是 config.json 覆盖

**我上轮的判断只对了一半**。v0.3.1 的 CI 地址注入确实生效了（本地验证 `go build -ldflags` 后公网地址出现 3 次；本机 `E:\AAProgram\easyShare\easyshare.exe` 里也确有 `47.96.128.231` × 3）。但这跟用户能否连上服务器**没有关系**。

真因在 `internal/config/config.go`：

```go
if strings.TrimSpace(value.PlatformBaseURL) == "" {   // ← 只在「空」时填默认值
    value.PlatformBaseURL = defaultPlatformBaseURL
}
```

早期 dev 版首次运行就把源码默认值 `localhost:8090` 写进了 `%LOCALAPPDATA%\EasyShare\config.json`（本机那份时间戳 10-15 22:52）。升级安装不清理该文件 → 字段非空 → **烘焙的公司地址对所有老用户一直是空转**。

**为什么流水线是绿的**：CI 断言只扫二进制里有没有那个字符串，看不到用户磁盘上已有一份旧配置。这层是整条链路的盲区。

**修法**：`shouldRebasePlatformURL(stored, baked)` —— 仅当「存量值是 loopback」且「烘焙值非 loopback」时改写为烘焙值并**落盘**。
判据刻意收窄成单向迁移，理由写进注释：
- 烘焙值本身是 loopback（本地 dev 构建）→ 不动，否则会把本地配置改坏
- 存量值已是外部地址（用户手工填的）→ 不动，那是用户的意图
- 存量值为空 → 不走这条，由原「空则填默认值」分支处理

### ② macOS 是变量名不匹配，地址压根没注入（我上轮方向错了）

```
build-mac.yml:80   echo "EASYSHARE_LDFLAGS=..." >> $GITHUB_ENV      ← 导出的是这个
build-mac.sh:14    PLATFORM_URL="${EASYSHARE_PLATFORM_URL:-}"      ← 读的是这个
```

两者不一致 → 脚本拿到空值 → `LDFLAGS=()` 为空 → Core 与 App 都没注入地址。构建全程无异常，只在产物断言才报「未找到 PLATFORM_URL」。

**关键教训**：第 11 步那个报错**是正确且珍贵的** —— 它抓到了真问题。我上轮把「断言失败」当成「断言写法有缺陷」，去改 `lipo -thin`，方向错了；那个改动本身无害（切片查确实比整文件 grep 更严，能同时拦住漏注入与半注入），但没解决问题。**断言报红时先信断言，别急着怀疑检查手段**。已把该段注释从「strings 会漏判」改成真实理由。

顺带堵静默通过：`GITHUB_ACTIONS` 环境下缺变量直接 `exit 1`（本地开发仍允许不设，那是连本机 RuoYi 的正常用法）。三种场景都实测过。

## 学习公众号文章《WMS库位不是编个号》（折哥善道，2026-10-17）

用户分享 WMS 库位管理文章，要求对照 EasyShare 找借鉴点。文章四件事一条线：库位是坐标（区-排-列-层四元组）不是编码；分区划黄金区；编码三件套（流水号/校验码/数字别名）；动线号定路径引擎派单顺序；上架靠前三节底座。核心论点：底座粒度决定算法上限。

对照知识平台（docs/knowledge-platform.md）的映射结论：
1. 切块/元数据粒度决定检索精度上限——结构感知切块即"编码定到列"，建议里程碑 2 Java 文件登记时规范块级坐标（file_id+version_id+章节路径+块序号）。
2. 分区思维 → 知识域分区 + 热冷分离（热文档缓存=黄金区）。
3. 文件身份三件套 = file_id（流水号）+ 内容哈希（校验码，防引错位）+ 可读路径（别名）。
4. 动线式调度 → 传输队列与检索编排沿预设序派发，不现算最优；规则外置按租户配置（与现有 JSON 清洗规则集同路）。
5. 盘点动线 → 知识健康度巡检按域分批。

注意类比边界：WMS 省的是物理米数，知识检索"顺线"省的是确定性与可解释性；实体货堆叠兼容性规则在对象存储场景不存在，不搬。

## macOS 打包断言假失败 + 网盘新建文件夹（用户报「mac 打包还是有问题」「学 WPS 钉钉连创建目录都没有」）

### ① macOS 第 11 步是**假失败**（v0.3.2 起）
- 报错「(x86_64) 中未找到 http://47.96.128.231:11054」，但同构建日志里 Wails 打印 `LDFlags | -X easyshare/internal/config.defaultPlatformBaseURL=...` → **注入是成功的**。
- 真因：macOS `strings` 默认只扫 initialized data section（`__DATA`），Go 字符串常量在只读段 → 扫不到。**Windows 侧走 ReadAllBytes 字节级扫描所以从未误报**。修法 `strings -a`（build-mac.yml 两处）。
- 定位手段：check-run annotations API **匿名可读**（`/repos/ersanzi/easy-share/check-runs/{id}/annotations`），比下载日志（要 admin）高效。本地 `GOOS=darwin GOARCH=amd64` 交叉编译 + binutils strings 验证 URL 连续存放。
- **教训**：断言报红先信断言内容再怀疑手段；上轮把「未找到」当「断言写法缺陷」改切片逻辑，方向错了。

### ② 新建文件夹 = 控制面补全（前端早预留）
- 前端 `driveFolder.ts` 的 isDirMarker / CloudPanel 面包屑 / 文件夹行**早就齐全**，只差创建入口。
- 目录 = RustFS 0 字节日志标记对象（键以 `/` 结尾）。`POST /easyshare/drive/mkdir`（幂等、无 es_file 行）；`GET /objects` 加 `includeDirs`（默认 false，**只有网盘页传 true**，挂载盘/WebDAV/快搜零传染）。
- 目录**不补账**（reconcileAndMap 挡掉）：补 file_size=0 行会污染秒传与回收站。
- 目录**删除即真删不进回收站**：`DELETE /object` 对无 active 行对象直接删对象（`storage.deleteDirectory`，`keyAt` 内 normalizeRelative 拒尾斜杠不能复用 deleteAt）。前端文件夹行删除按钮，**非空拒绝**（递归删事务边界未解决）。
- 栈：Java DriveController/DriveStorage/DriveFileService + Go client.go(Mkdir/ObjectsWithDirs)/app.go(CloudMkdir) + 前端 CloudPanel/App.vue/core.ts/style.css。

### ③ macOS CI 三轮追记（v0.4.0 发布过程中，最终双平台全绿）
- **真因实锤**：前几轮「(x86_64) 中未找到地址」全是 macOS `strings`（BSD）段语义误报——连 `CGO_ENABLED=0` 的 Core（本地同款 `go build -ldflags`，binutils strings 稳定命中 3 次）都判缺失。**修法：python3 字节级 `in` 判定**（与 Windows ReadAllBytes.Contains 同语义），strings 降级为对照。
- 排除的假说：`-s -w` 与 `-X` 冲突（实验排除）；GOFLAGS 传 -X（按空格切 flag，不通）；pipefail+SIGPIPE（本地 GNU strings 复现不了）。
- **排障渠道**：check-run annotations API **匿名可读**（`/check-runs/{id}/annotations`，id 从 `/commits/{sha}/check-runs` 拿，注意 run id ≠ check-run id）；日志下载要 admin、artifact 匿名下载被拒。诊断行走 `::error::` 前缀才进 annotations（普通 echo 被摘要 `tail -n 200` 挤掉）。
- **YAML 坑**：`run: |` 块标量内 python3 多行 `-c` 第二行顶格 → 被当新键 → workflow 语法错误。**多行代码必须单行化或保持缩进**；本地验证用 `frontend/node_modules/yaml`（node -e require 解析）。
- 发布流程：tag 删重打（`git push origin :refs/tags/vX` + 本地 `git tag -d`）后在新 commit 重打；Gitee 推送常遇 schannel TLS 失败，重试 2-4 次即好。
- **结论：字节级判定是跨平台唯一可靠的产物内容检查**；断言报红先信内容再疑手段，但手段也可能是错的——「查完全场再说话」。
