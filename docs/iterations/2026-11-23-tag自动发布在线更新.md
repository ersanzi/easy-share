# 正式 tag 自动发布到在线更新源

## 用户问题

打正式 tag 已触发安装包构建和 GitHub Release，但客户端只检查 RuoYi 控制面的 `/easyshare/app/latest`；两条链路未接通，仍须手工运行发布脚本。

## 目标

- 正式 tag 的对应平台构建成功后，自动上传安装包并发布到控制面在线更新源。
- tag、源码版本与包内版本一致；预发布和手动构建不进入普通更新源。
- 凭据只通过 CI secrets/environment 注入；重复发布相同资产可安全重跑，不覆盖不同正文的正式版本。
- 回归能模拟上传、发布、匿名清单和下载校验，失败时明确报红。

## 非目标

安装器更新助手/失败回滚、客户端切页状态、差分更新、百分比灰度，以及真实推送、打 tag、发布或服务器部署。

## 设计决策

保留控制面更新源与现有 GitHub 分发，不让客户端依赖 GitHub。Windows/macOS 工作流各增独立 `publish-update` 任务，只在正式 tag 的对应平台构建成功后运行；下载当前 run 的资产，不扫描其它提交或历史 Release。发布任务共享串行组避免同版本并发登记；凭据仅注入发布步骤。

构建阶段校验三处版本/tag及 Windows 产品版本/macOS App plist；随包记录提交、目标、版本和 SHA256，发布前再验证。统一 Node 22 发布器实现先查已有版本、相同资产只回验、不同正文拒绝覆盖、旧 tag 不替代更高正式版本、pending 相同资产重试。完成上传/发布后核对匿名清单全字段并真实下载流式验证大小和 SHA256。PowerShell 5.1 兼容入口共用该实现，去掉 localhost/默认口令回退，旧参数保持但凭据不进入 Node 命令行。

没有改 Java API：防覆盖等规则属于统一发布器，原管理 API 仍保留兼容语义。没有增加安装器事务/回滚，不能将此轮发布验证扩称为客户端安装成功验证。

## 兼容与迁移

保持 `/easyshare/app/*` 协议、现有手动发布入口与客户端配置兼容；CI 首次接入需要配置发布目标与专用发布凭据。正式包更新仍要求先投递兼容的服务端及 SQL。

## 测试计划

先运行确定性回归确认 tag workflow 未接通控制面；随后对发布脚本做本地 mock HTTP 验证，不连接生产。执行文档引用、脚本语法与受影响回归。

## 发布与回滚

仅交付源码配置；实际 tag 和外部发布另获用户授权。CI 配置未齐不能静默跳过或谎称在线更新已发布。
