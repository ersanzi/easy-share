# 会议听记：实时上屏与发言人标注（2026-10-20）

## 用户问题

用户实机反馈四条，原话分别是「不能使用」「切到别的地方就中止了」「不支持流式展示识别内容」「发言人也不能支持更新，比如我标注发言人1是 xxx」。拆开看是四个独立缺陷叠在一起：

1. **切页即中断**：录音状态挂在 `MeetingsPanel` 组件里，路由切走 → 组件卸载 → 采集与推流一起停。
   前一轮已经把采集提到 `meetingSession` 单例，但**推流仍走浏览器 `fetch`**，组件卸载后请求照样被打断，
   表现就是「录音还在，但字不再出，回来一看停在中途」。
2. **不出字 / 看起来像坏了**：推流是 600ms 一片的同步往返，任何一次慢回包就把整条队列堵住；
   旧实现「一断就收摊」（`liveState=unavailable`，清空队列，之后整场不再上屏）；
   而断行要等 40 字或句号，一句短话在界面上长时间没有任何变化。用户无法区分「在识别」与「卡死」。
3. **发言人改不了**：改名接的是 `PATCH /speakers`，但面板把「改完」当成「后端已生效」；
   重新转写时序号会被重聚类重排，旧序号上的人工标注会被原样贴到新序号上（张冠李戴），
   且没有「合并发言人」这种同一人被拆成两簇时的补救手段。
4. **逐字稿不能改**：识别错的字只能整场重新转写，没有单句修正入口。

## 目标

- 切到任何页面（含最小化窗口）录音与实时字幕都继续；回来能看到断线期间的字。
- 上屏节奏可感知：说完一小句（逗号级语义块）就出字；界面给出「N 秒前出过字」，能区分停顿与卡死。
- 任何一次推流失败都能自愈：先拉服务端会话快照续上，连续失败才降级为轮询兜底，**录音永不受影响**。
- 发言人可改名、可合并；重新转写不会把人工标注安到别人头上。
- 转写正文可逐句修正，且修正过的句子有记录。
- 会中能主动核对事实口径（数字/期限/人名），不必等录音结束。

## 非目标

- 不做实时声纹（流式模型只有 ASR，没有说话人分离）——实时字幕仍是「无发言人」的预览，终态以离线重跑为准。
- 不做实时字幕与终态转写的文本对齐/回填（两套模型，逐字稿以离线结果为准）。
- 不改会中要点的 LLM 提示与节奏（仍是每 8 行触发一次）。
- 不做发言人重命名后的「历史笔记同步改称」以外的事情（纪要/导图需用户点「按模板重生成」）。

## 设计决策

### 1. 推流主通道改走 Wails 绑定（`MeetingStreamChunk`）

`fetch` 属于渲染进程的文档上下文，组件卸载/页面切换时请求会被中止；而 Wails 绑定调用
不挂在组件生命周期上。同一份 `meetingSession` 单例里，`recorder → enqueueChunk → core.meetingStreamChunk`
全程与组件无关。`/kapi/meetings/*` 同源网关只保留真正的大流量通路（整段上传、音频回放、导出）。

单片上限 `streamChunkMaxBytes = 256KB`（600ms@16k ≈ 19KB 的 13 倍余量）：超限**只丢这一片**，
不中断会话——上屏少几个字，离线重跑补齐。

### 2. 自愈式的推流队列（`meetingSession.pumpStream`）

- 单片调用有 12s 超时（`STREAM_CALL_TIMEOUT_MS`）。模型实测 RTF 0.33~0.58，12s 已是 20 倍余量。
  超时后该请求从队列摘掉，界面不阻塞。
- 失败 → `resync()` 拉 `GET /meetings/{id}/stream/live` 把服务端已有内容续到屏幕，再继续推下一片。
  这样偶发抖动对用户完全透明（只是慢一拍）。
- 连续 3 次失败 → 降级 `degraded`：停止推流、每 3 秒轮询快照，录音继续。
  刻意不做「降级后自动恢复推流」：半通不通时来回闪状态比稳定兜底更差。

### 3. 服务端会话状态（`GET /meetings/{id}/stream/live`）

`stream.py` 的会话快照补三件事：`recording`（会话是否还在——进程重启/闲置回收后为 false，前端据此改为只等离线重跑）、
`last_line_at`（最后一行上屏的录音秒数）、`recent`（最近 3 行，给快检用）。锁粒度也改了：
会话表锁只保护容器读写，**推理在会话自己的锁里跑**——旧实现 feed 持全局锁跑模型，
两场会议并发时互相堵死，前端那一侧就表现为「久等无回包」。

### 4. 断行与热词

- 断行改成「句末标点 或 逗号级标点 或 ≥24 字」（`knowledge/app/meetings/livenow.py` · `should_break`）。
  旧规则 40 字才断，视觉上等于「半天不出字」。
- 流式模型也吃 `hotword`（与离线同口径，按录制者热词表）。旧 funasr 版本不认该参数时捕获 `TypeError` 退化。

### 5. 会中快检（`POST /meetings/{id}/live-check`）

只喂**最近 4 行**（不是整场）给 LLM，输出 `{verdict, note, points}`，`verdict ∈ ok|attention|unclear`，
失败返回 `unavailable`（不抛 500）。前端节流：新增 ≥3 行、累计 ≥6 行、20 秒内最多一次，另有手动按钮。
这是「会中能救场」的口径——整场纪要要等录音结束。

### 6. 发言人：合并 + 重新转写时不张冠李戴

- `POST /meetings/{id}/speakers/merge`：把一位的全部轮次并给另一位，相邻同人段落顺手拼上。
- 重新转写：`initial_speaker_names` 仍保留人工标注；但 `apply_voiceprints` 改为
  「声纹指向另一人时以声纹为准」——模型重聚类后序号变了，硬留旧名就是张冠李戴。

### 7. 逐字稿可编辑（`PATCH /meetings/{id}/segments/{index}`）

只改这一句的文字，说话人与时间轴不动；改过的下标进 `edited_segments`。

## 兼容与迁移

- 记录 JSON 只多一个可选字段 `edited_segments`，旧记录读出来按空数组处理，无需迁移。
- API 只新增，不改既有签名；`MeetingLiveView` 新增字段对旧前端是忽略项。
- Wails 绑定新增 5 个导出方法，已 `wails generate module` 重生成并同步 `types/core.ts`、`services/core.ts`。
- 推流从 `/kapi` 网关挪到绑定：网关仍保留旧路由（未删除），便于回滚。

## 桌面端点验结果（2026-10-20 18:20–18:45）

构建：`go build -o build/bin/easyshare-core.exe ./cmd/core` + `wails build -skipbindings`。
**坑**：`wails build -clean` 会把 `build/bin` 整个清掉，连刚编好的 core 一起删——先 `wails build` 再编 core，或干脆别加 `-clean`。

用真实录音（`9dfb0e6a…wav` 前 24s）经 Core 网关 `POST /api/knowledge/meetings/{id}/stream` 逐 600ms 推送：

| 检查项 | 结果 |
| --- | --- |
| 开会话 / 推流 / 快照 `stream/live` | 全部 200；`recording=true`，行数与时长正常 |
| 实时出字 | **正常**，中文正确：`[0s] 同时我们开始今天的周会…`、`[7s] 演示的准备情况…` |
| 稳态 RTF（模型已热） | 0.42~0.50（上一轮活栈记录 0.303，同为 CPU 单流，差异来自本期负载） |
| 冷加载首片 | 72s（本次系统负载下），与 14~88s 实测区间一致 |
| 发言人改名 | `PATCH /speakers` 200，`speaker_names` 落盘 |
| 合并发言人 | `POST /speakers/merge` 200：2 人并成 1 人，12 段按相邻合并成 8 段 |
| 逐字稿改字 | `PATCH /segments/0` 200，文字与 `edited_segments:[0]` 均落盘 |
| 会中快检（上游 LLM 503） | **5.3s 返回 `verdict=unavailable`**（见下方两处修复） |

点验中发现并修掉两个真问题：

1. **实时字幕时间戳打在了断句时刻**：`_flush` 用的是 `elapsed_seconds()`（此刻总共喂了多少音频），
   于是同一段 0:03 开始的话被打成 `[7s]`、下一句 `[16s]`——看起来每句话都说了七八秒才停。
   改为记录**这句话第一个字**落进来时的采样位置（`knowledge/app/meetings/stream.py` · `current_start_samples`），
   点验后时间戳变成 `[0s]` / `[7s]`，与离线逐字稿轴一致。回归用例
   `test_stream_line_timestamp_is_sentence_start_not_break_moment`。
2. **快检在 LLM 挂掉时变成「连接被关闭」而不是降级结果**：上游 503 时 summarizer 按
   0.5/1/2/4/8/16s 退避重试，一次快检能拖到 120s+，正好撞上 Core 的 `knowledgeQueryTimeout`。
   两层修复：① `live_check` 只给 1 次尝试（`engine/minutecraft/summarizer.py` · `ask_json` 的 `max_attempts`），
   秒级路径不该跟整份纪要共用退避链；② 知识服务侧再兜 25s 硬上限
   （`knowledge/app/meetings/routes.py` · `_live_check_timeout_seconds`），Core 侧把等待收到 20s
   （`internal/api/knowledge.go` · `knowledgeLiveCheckTimeout`）——两边都留「降级结果走得回来」的余量。
   点验后 5.3s 即返回 `unavailable`。

**未覆盖**：屏幕共享音源、真实会议室长时录音、切页时的肉眼观感（这三项要人工开着窗口操作，
本机自动化只能到 HTTP 层）。界面文案与状态点位置按代码与 CSS 复核，未做像素级截图比对。


## 已知问题与下一步

- **实时字幕无发言人**：流式模型没有说话人分离，实时阶段只能给「谁说了什么」的终态。钉钉在会中也只显示
  文本流、发言人标注在结束后整理，本仓与之同口径。
- **会中快检依赖 LLM 配额**：本地实测上游网关返回 429/503 时快检降级为「AI 不可用」，不影响录音与上屏。
- **服务端内存会话不随进程重启保留**：录音中若知识服务重启，`stream/live` 会回 `recording=false`，
  前端按设计转为「只等离线重跑」——录音本身在本地采集端，不受影响，但这一次的实时字幕会丢。

## 手工验收清单（真机，需人工开窗口操作）

1. 开始录音 → 立即说话 → 3 秒内看到第一行字；标题旁显示「N 行 · 边说边出字」，「N 秒前」持续跳动。
2. 录音中切到「网盘」「设置」再切回：计时连续、字幕行数只增不减；切页期间说的话出现在列表里。
3. 停止 → 等待转写完成 → 发言人卡片点名字改成「张三」→ 转写行立刻变名；点「合并」把另一簇并进来。
4. 转写正文点「改字」修正一句 → 刷新页面后仍是修正后的文字。
5. 录音中观察「N 秒前」：长时间无人说话时提示「已 N 秒没有新内容（可能在停顿…）」，而不是空白卡住。
6. 录一段线上会议（「系统声音+麦克风」音源）：确认共享选择器勾选系统音频后，对方发言也上屏。

第 1、3、4、5 项的后端行为已在 2026-10-20 的桌面端点验中用 HTTP 全链路验证过（见上节表格）；
剩下的是界面观感与音源采集，需要在真实窗口里肉眼确认。
