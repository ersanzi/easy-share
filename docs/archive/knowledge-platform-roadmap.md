# 知识平台下一步规划

> 本文是知识平台里程碑 1–3 的执行规划。愿景与架构见 [`knowledge-platform.md`](knowledge-platform.md)，进度见 [`progress.md`](progress.md)。
> 里程碑 0（Python AI 服务骨架）已完成，管线端到端跑通。
> 最后更新：2026-07-22

## 规划原则

- 延续 walking skeleton：每个里程碑先跑通该层的最薄闭环，再加厚。
- 串行依赖、内部并行：里程碑 1→2→3 有先后依赖，但每个里程碑内部的子任务可并行。
- 每一步都要有可验证的交付物，不做"无法验收"的工作。
- 工作量标注：S（约 1–2 天）/ M（约 3–5 天）/ L（约 1 周以上）。

## 里程碑 1：知识库能力增强

**目标**：让知识库真正可用，检索质量达到"问答靠谱"的水平。这是后续一切的地基——检索不准，权限和 WPS 都无从谈起。

**前置**：里程碑 0 已完成；需确定 embedding 提供方。

### 1.1 解析层扩展（M）

| 任务 | 说明 |
| --- | --- |
| xlsx 解析 | openpyxl/pandas，按 sheet + 行列转文本，保留表头 |
| pptx 解析 | python-pptx，提取每页文本与备注 |
| html/htm 解析 | beautifulsoup，去标签取正文 |
| 解析降级与日志 | 单文件失败不影响批量，记录失败原因 |
| 扫描件 OCR（可选，L） | pytesseract 或 PaddleOCR；视实际需求决定是否纳入 |

### 1.2 切块与清洗改进（M）

| 任务 | 说明 |
| --- | --- |
| 结构化切块 | 按 Markdown 标题 / docx 段落样式 / PDF 章节切，而非纯定长 |
| 句子边界切块 | 定长切分时在句号/换行处断开，避免切断语义 |
| 切块元数据 | 记录所属章节标题、页码、序号，用于溯源展示 |
| 文本清洗 | 去页眉页脚、水印、多余空白、重复段落 |

### 1.3 向量库升级（M）

| 任务 | 说明 |
| --- | --- |
| 换 Chroma | 本地持久化、原生支持元数据过滤，替换内存+JSON 实现 |
| 接口不变 | 保持 add/delete_doc/query，上层无感 |
| 增量更新 | 文档变更时 delete_doc + 重新入库，避免全量重建 |
| 规模化评估（可选） | 数据量大时评估 Milvus |

### 1.4 检索增强（S–M，可选）

| 任务 | 说明 |
| --- | --- |
| 混合检索 | 向量 + 关键词（BM25）融合，提升专有名词命中率 |
| 重排序 | 检索后用 rerank 模型精排 top-k |

### 交付物

- 支持 txt/md/docx/pdf/xlsx/pptx/html 解析
- Chroma 持久化向量库，增量更新
- 结构化切块 + 元数据溯源

### 验收标准

- [ ] 给定一批真实混合格式文档，全部成功解析入库
- [ ] 换词提问（与原文用词不同）仍能命中相关片段
- [ ] 文档更新后重新入库，问答反映新内容
- [ ] 检索片段带章节/页码溯源信息

## 里程碑 2：Java 控制面 + 企业级

**目标**：从单机工具走向多用户企业级——账号、权限、自动入库、权限感知检索。

**前置**：里程碑 1 检索质量达标。

### 2.1 Java 业务服务（L）

| 任务 | 说明 |
| --- | --- |
| 服务骨架 | Spring Boot + MyBatis-Plus（复用 qn-trusted-connector 经验），置于 `platform/` |
| 账号与认证 | 注册/登录，JWT 或 SSO |
| RBAC 权限 + 多租户 | 角色、权限点、租户隔离 |
| 文件登记表 | id、名称、所有者、权限、状态、RustFS key、与 Python 向量记录共用文件 ID |
| 业务库 | MySQL/PostgreSQL；分析用 Doris |

### 2.2 权限感知检索落地（M）

| 任务 | 说明 |
| --- | --- |
| 权限裁决 | 提问时 Java 算出用户可访问的文档 ID 集合 |
| 传过滤条件 | 把 doc_ids 传给 Python `/query`，只在范围内检索 |
| 文件级权限 | 支持按所有者/角色/部门控制文件可见性 |

### 2.3 自动入库管线（M）

| 任务 | 说明 |
| --- | --- |
| 消息队列 | RabbitMQ 或 Kafka（此阶段定选型） |
| 上传触发解析 | 文件上传到 RustFS 后，Java 发任务 → Python 消费解析入库 → 回写状态 |
| 删除/更新同步 | 文件删除/更新时同步删除/重建向量 |
| 入库状态可查 | 文件登记表中记录解析状态（待处理/成功/失败） |

### 2.4 与 EasyShare 桌面端集成（M）

| 任务 | 说明 |
| --- | --- |
| 桌面端登录 | EasyShare 增加账号登录 |
| 上传走服务端 | 上传经 Java 服务（而非桌面端直连 RustFS），纳入文件登记与自动入库 |
| 保留局域网直传 | 局域网传输能力不变，与云端上传并存 |

### 交付物

- Java 控制面服务（账号/权限/文件登记/编排）
- 上传后自动解析入库的异步管线
- 权限感知检索真正生效
- EasyShare 桌面端登录 + 走服务端上传

### 验收标准

- [ ] 两个用户数据完全隔离，互不可见
- [ ] 用户只能检索到自己有权限的文档
- [ ] 上传文件后无需手动操作，自动可问答
- [ ] 删除文件后问答不再命中其内容

**前置**：里程碑 2 的账号体系与 AI 助手 API。

### 验收标准

## 依赖与关键路径

```
里程碑 1（知识库增强）──→ 里程碑 2（Java 控制面）──→ 里程碑 3（WPS 插件）
   检索质量是地基            账号权限是前提            交付层
```

- **关键路径**：1 → 2 → 3 串行。里程碑 1 的检索质量直接决定最终产品价值，最值得投入。
- **内部并行**：里程碑 1 的解析/切块/向量库可并行；里程碑 2 的 Java 服务与消息管线可并行。
- **尽早确定**：embedding 提供方（影响里程碑 1 检索质量）、向量库选型（里程碑 1 早期）、消息队列选型（里程碑 2）。

## 风险与待决策

| 项 | 说明 | 何时定 |
| --- | --- | --- |
| embedding 提供方 | 需支持 embedding 的 OpenAI 兼容端点，或本地 sentence-transformers | 里程碑 1 开始即定 |
| 向量库选型 | Chroma（轻）vs Milvus（规模化） | 里程碑 1 早期 |
| OCR 是否纳入 | 扫描件解析，PaddleOCR 较重，看实际需求 | 里程碑 1 |
| 消息队列选型 | RabbitMQ vs Kafka | 里程碑 2 |
| 文件 ID 体系 | Java 登记与 Python 向量共用的稳定 ID 规则 | 里程碑 2 |
| 数据出域合规 | 云端 LLM 的企业合规性，私有化部署口子的落地 | 里程碑 2–3 |
| WPS 插件分发 | 企业内部署与版本管理方式 | 里程碑 3 |
