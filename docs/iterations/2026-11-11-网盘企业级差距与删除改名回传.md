# 网盘企业级差距分析 + 资源管理器删除/改名回传（2026-11-11）

## 背景与目标

用户指令：接着迭代网盘，用 REA 技术分析 WPS 网盘、钉钉与既有调研项目（Cloudreve），找出还差什么，
让网盘「真正能被企业使用起来——现在不是一个真正的网盘项目」。

本迭代做两件事：
1. **差距分析**：在 2026-10-16 七切片路线图全部落地、2026-11-08 个人云盘云端主存合入之后，
   重新对账「企业真实使用」还缺什么，给出优先级。
2. **实现头号缺口**：资源管理器里的删除/改名/移动不回传远端——云端主存形态下这是信任崩塌级的行为缺陷。

## 二、本轮 REA 取证（2026-11-11 新增）

目标：钉盘 `sync_frame.dll`（SHA-256 `4697e02d…efc4`，与 2026-10-16 同一目标），复用持久 Ghidra 工程
`output/ghidra-proj`（dingpan），`ProbeStrings.java` 定向挖掘**删除/改名回传的护栏与状态机**。

### 新增结论

1. **企业策略可否决本地删除，且否决后远端权威**【G】：用户可见通知模板
   `Delete event ignored by enterprise settings. File will re-establish local placeholder \n{}`
   （`FUN_180591ab0` 通知表，与「admin disabled local sync」「Storage capacity limit reached」等同一注册函数）。
   语义：删除不传播时，远端保留，本机占位符**重建**回到与远端一致——远端是主存，本机是投影。
2. **恢复路径会重设占位符 PinState**【S→REA】：`restore sync state, path: {}` 位于钉盘自建
   `cloud_filter_fuse\cf_fuse_node_impl.cpp`（`FUN_18051e5d0`），对恢复的路径逐个
   `CfSetPinState(…, INHERIT, RECURSE)` 并在失败时记 `cf_state_set_include_recurse … failed`——
   钉盘把「远端/回收站恢复」落地为占位符重新投影，钉住状态跟随恢复。
   REA 正式 Evidence：`ev_b61b1f94c30eb13b309fb95f29dbbcc5a8e15012bf27aa32fdc210adc5a32fa0`
   （`output/rea-evidence-restore-pinstate.json`，Ghidra 12.1.4 / JDK21 / 6.8.0）。
3. **旧版本清理走系统回收站**【G】：`remove_all_old_dpsync_version: … trying move_to_trash`
   （`FUN_1804fc6f0`）——同步引擎自己的清理动作也进回收站，不静默物理删除。
4. **WPS 侧佐证（差距 #2 的设计输入）**【G】：ksyncengine.dll 存在 `CfUpdatePlaceholder`
   的懒加载 thunk（`FUN_10088ce0`，GetProcAddress 动态解析 cldapi.dll）——远端变更走
   「只更占位符元数据、不下正文」的投影更新，与我们的 tree sync 同机制；
   `RemoteModify`/`CfRevertPlaceholder` 在定义数据中无独立串（探针未命中）。
   「远端更新刷新已水合正文」的精确策略（静默替换 vs 冲突副本）需 qingnse64 工程续挖，列为差距 #2 开工首问。
5. **未取到（记录边界）**：本地事件→远端 RPC 的精确防抖窗口。`already has pending delay task`
   命中在 `upgrade.cc`（docbrowser 升级调度），与同步事件调度无关；`renameDentry/moveDentry/deleteDentry`
   RPC 路径串为整块数据，ProbeStrings 未按独立 data 命中（2026-10-15 已从 RPC 注册表确认三者存在）。

### 方法论照旧

- 持久工程探针【G】+ REA 正式 Evidence【S】分层引用；Ghidra 工程锁坑：analyzeHeadless.bat 结尾

## 四、本切片设计：删除/改名/移动回传（扫描差分 + NTFS 身份连续性）

### 为什么不用事件监听（与钉盘/WPS 的差异说明）

钉盘与 WPS 都用 `ReadDirectoryChangesW` 事件流（改名/移动不走 CfApi 回调）。我们**刻意先不上事件流**：
- 桌面挂载已有 5 秒 reconcile 节拍（`cfapiSyncInterval`），扫描差分的时延上限就是 5 秒，接近实时；
- 事件流要解决离线补账、乱序、去抖一整套问题（钉盘为此建了 remote_history 表 + 恢复状态机）；
- NTFS 枚举语义给了扫描差分一个事件流没有的优势：**枚举不到 = 强证据**（FindFirstFile 属性枚举
  不需要打开文件，占位符/占用文件均可枚举；单个枚举错误会让整个 WalkDir 报错中止而不是静默缺项）。

### 推断规则（全部以「远端清单 + NTFS 身份」双重对账，不做单向臆断）

每 tick 在上传循环**之前**跑回传（保证改名目标不被当作新文件重新上传、fileId/版本得以保留）：

1. **改名/移动**：记录 A 缺席 + 新路径 B 的 NTFS FileId 与 A 记录持久化的身份一致且大小一致
   → `POST /move`（fileId 不变，回收站不留副本）。远端 A 已缺席视为「上次移动已生效」自愈；
   远端 B 已被占用 → 保守报 issue（不移动、不删除）。
   目录移动接受后，子树记录/远端映射/seen 键整体改前缀。
2. **删除**：记录 A 缺席连续两个 tick（missingSince ≥ StableFor）→ 软删进**云端回收站**（可还原，
   对齐钉盘「删除可恢复」语义；目录走递归软删）。身份护栏：远端 A 的 FileId 与记录不一致时不删
   （防止「另一个客户端已删 A 又传了新文件」时误删别人的文件）。
3. **空根守卫**：本地一个条目都没有而记录 >0（同步根被整体清空/磁盘故障）→ 本 tick 拒绝一切删除/移动推断。
4. **失败语义**：远端操作失败保留记录与保护，下个 tick 重试；save 失败整 tick 中止（与上传路径同规）。
   自愈锚点是**远端清单**（幂等：move 已生效=A 缺席；delete 已生效=A 缺席），不引入新持久化状态机。

### 前提与改动面

- 记录持久化 NTFS 身份（`writebackRecord.Identity`，volumeSerial+fileId hex），改名推断跨重启有效；
  旧记录无身份 → 退化「删+建」（内容都保留：A 进回收站、B 正常上传），首个观察周期后全部补齐身份。
- 新可选接口 `cfmount.DeleteMover`（MovePath/DeletePath/DeleteTreePath）：`drive.Client` 现有
  `Move/Delete/DeleteTree` 签名完全一致，零装配改动（`nativeWritebackConfig` 传的 client 天然满足）。
- 目录记录补存 `FileID`（CreateDirectory 已返回），删除优先走 `DeleteTreeByFileID` 身份删除。
- 身份读取注入点 `WritebackConfig.IdentityFor`（默认 `writebackFileIdentity`），引擎测试平台无关。

### 明确不做（本切片）

- 不做事件流（ReadDirectoryChangesW）、不做离线事件日志（记录本身即日志）；
- 不做「删除确认弹窗」（回收站即确认，对齐钉盘静默+可恢复）；
- 不动共享空间 WebDAV 通路（spacedav 的 Rename/RemoveAll 早已双向）；
- 不做冲突弹窗（沿用既有「冲突副本/保守 issue」语义）。

## 五、实现对设计的两处修正（实现即文档）

1. **目录删除走路径 + 清单身份护栏，而非 DeleteTreeByFileID**：删除前先对远端清单核对
   `FileId == 记录.FileID`，与文件路径删除同一护栏，语义一致且少一次参数传递。
2. **空根守卫只挡「首轮扫描」**：初版按「本地空且记录>0 就拒绝」实现，单文件根删掉唯一文件
   即被误拦（单测当场抓到）。修正为守卫只作用于引擎首轮成功扫描——挡的是挂载时刻
   「占位符尚未建起/同步根整体丢失」，首轮见到过内容之后的空根视为用户清空，
   仍走两轮确认 + 回收站软删。重启后的首轮同样受守卫保护一轮。
