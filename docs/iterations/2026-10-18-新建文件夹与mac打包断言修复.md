# 2026-10-18 macOS 打包断言假失败 + 网盘新建文件夹

用户报两件事：**「mac 打包还是有问题」**、**「让你学习 WPS 和钉钉，连创建目录都没有」**。
两个问题根因完全不同，分开记录。

---

## ① macOS 打包：不是没注入，是断言扫不到

### 现场

v0.3.2 的 macOS Build 又挂在第 11 步「校验并整理产物」，check-run 注释给了确定答案：

```
build/bin/easyshare.app/Contents/MacOS/easyshare (x86_64) 中未找到
http://47.96.128.231:11054——ldflags 注入失败，产物不可发布
```

而**同一份构建日志**里 Wails 自己打印的配置行是：

```
LDFlags | -X easyshare/internal/config.defaultPlatformBaseURL=http://47.96.128.231:11054
```

注入参数确实传进去了。上轮（v0.3.2）修的是「变量名不匹配导致压根没注入」，那轮之后注入是成功的——**这次是断言本身在误报**。

### 根因：macOS `strings` 默认只扫 initialized data section

- Go 的字符串常量在 Mach-O 的只读段（`__TEXT`/`__cstring` 一带），不在 `__DATA`；
- macOS（BSD）`strings` **默认只扫 initialized data section**，要扫全文件必须 `-a`；
- Windows 侧同一处检查走 `ReadAllBytes` + `Encoding.ASCII.GetString` + `.Contains()`，**字节级全文件扫描，没有段的概念**，所以同样的注入在 Windows 上从未误报。

两边查法不同，不是「Windows 注入了、macOS 没注入」。

本地交叉编译验证过前提：`GOOS=darwin GOARCH=amd64` + 同款 ldflags 编出的 core，binutils `strings`（默认全文件扫）能稳定命中地址 3 次——**URL 在产物里是连续存放的**，注入机制没问题。

### 修法

`.github/workflows/build-mac.yml` 的 `verify_baked_url`：`strings` → `strings -a`（fat 切片路径与非 fat 回退路径都改，命中计数同步）。逐架构 `lipo -thin` 的切片检查保留——它拦的是「半注入」（只有一个架构有地址），与本次问题无关但不能丢。

### 教训

**断言报红时先信断言的内容，再怀疑断言的手段**。上轮把「未找到地址」当成「断言写法有缺陷」去改切片逻辑，方向就错了；这轮的报错文案其实一直准确地描述着「这个切片里没有这个字节」——只是原因在扫描方式，不在注入。看 check-run 注释（匿名 API 可读）比下载全量日志高效，这次就是靠它定位的。

## ② 新建文件夹：前端早就预留了目录识别，缺的是控制面

### 现场

前端 `utils/driveFolder.ts` 的注释写着「**权威目录层将来落控制面，本模块只做视图推导**」，且早已实现 `isDirMarker` 识别（key 以 `/` 结尾 = 目录占位，只贡献文件夹、不作为文件）；CloudPanel 有面包屑、文件夹行、`enterFolder` 一整套导航。**唯独没有创建入口**——控制面没有 mkdir 端点，且 `DriveStorage.listAt` 主动过滤掉尾斜杠对象（建了也看不见）。

所以这不是「加个按钮」的事，是把控制面这一侧补全。

### 实现（跨四层）

**控制面（platform-drive）**
- `DriveStorage.createDirectory(prefix, relative)`：put 0 字节、`contentType=application/x-directory`、键以 `/` 结尾的标记对象。重复创建幂等（PutObject 覆盖同内容），与本地文件系统行为对齐。
- `DriveStorage.listWithDirs(prefix)`：不过滤尾斜杠对象的新列举，**只给 `/objects?includeDirs=true` 用**；`listAt` 保持原样，挂载盘 / WebDAV / 快搜 / 增量列举行为零变化。
- `POST /easyshare/drive/mkdir`（MkdirBo{path, space} → MkdirVo{path}）：`normalizeRelative` 复用既有校验（拒空、拒首尾斜杠、拒 `.`/`..`、拒控制字符）；共享空间先过 `checkSharedWritable`。
- `GET /objects` 加 `includeDirs` 参数（默认 false）。
- `DriveFileService.reconcileAndMap`：目录标记对象**不补账**——补一行 file_size=0 的「文件」会污染秒传判定（同哈希 0 字节文件误判已存在）与回收站语义。
- `DELETE /object`：path 带尾斜杠判定为目录，剥斜杠后走解析；**markRecycled 返回 null（无 active 行）时直接删对象**。这同时修掉一个既有缺口：目录建了没有任何删除手段（软删找不到行就不删对象，且带斜杠路径过不了 normalizeRelative）。目录键拼接送 `deleteDirectory`（`keyAt` 内部的 normalizeRelative 拒尾斜杠，不能复用 deleteAt）。

**Go 端**
- `drive.Client.ObjectsWithDirs`（Objects 内部复用，加 `includeDirs=true`）；`drive.Client.Mkdir`。
- `App.CloudMkdir(targetDir, name)`：与 CloudUploadPaths 的 targetDir 语义一致；name 校验与 CloudRename 同款（拒分隔符、拒 `.`/`..`）。
- `App.CloudList` 改用 ObjectsWithDirs（网盘专用出口）；`driveObjectToFile` 对目录 key 先 TrimRight 再取 Base。

**前端**
- `services/core.ts` 加 `cloudMkdir`；CloudPanel 工具栏加「新建文件夹」按钮 + 名称输入浮层（打开即聚焦、Enter 提交、复用 move-dialog 样式）；文件夹行加「删除」按钮——**非空时拒绝并提示先清空**（递归删子树的事务边界没解决之前，不给「看起来删掉了、实际文件还在」的入口）。
- App.vue 删除确认按 key 尾斜杠区分文案：目录是**真删、不进回收站**，不能沿用文件的「可在回收站还原」。

### 踩坑记录

1. **fat jar 被运行中的服务锁住**：`spring-boot:repackage` 报 Unable to rename。停服务（TaskStop 只杀 powershell 包装，java.exe 子进程要 `taskkill /F /PID` 补刀）→ 重打包 → 重启。
2. **新代码没生效的误判**：删目录报「文件路径不能以 / 结尾」，一度怀疑 jar 是旧的。从 fat jar 里抠出嵌套的 `BOOT-INF/lib/easyshare-drive-6.0.0.jar` 验字节码（`/+$` 正则在），确认代码是新的——真因是 `deleteAt → keyAt → normalizeRelative` 又拒了尾斜杠，才引出 `deleteDirectory`。
3. **服务日志是最后的裁判**：PlusWebInvokeTimeInterceptor 打出了 DELETE 的入参和随后的 SQL（`file_path='待删空目录-020128'` 已剥斜杠），一眼定位错误发生在 markRecycled 之后的 deleteAt。
4. **live 测试的假通过**：`findObject` 走默认列举（不含目录），拿它断言「目录已删除」永远为真。目录相关断言必须走 ObjectsWithDirs。

### 遗留

- **非空文件夹删除未做**（需递归删子树 + 事务边界设计），前端已挡住并提示。
- 目录不进 `/changes` 增量流：挂载盘看不到新建文件夹（它的目录语义本就独立），网盘页全量列举不受影响。
- 控制面未部署到公网（47.96.128.231:11054）前，桌面端点「新建文件夹」会 404——需随下个版本发布控制面。
- 递归删、目录分享、目录级权限留待后续切片。
